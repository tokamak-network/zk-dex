# H1. ZK Light Client Bridge

영지식 증명을 사용하여 전체 노드를 실행하지 않고도 소스 체인 합의를 검증하는 무신뢰 크로스체인 브릿지.

**요구사항**: ZK-SNARK verifier contract | Consensus proof circuits | Header relay infrastructure

---

## 배경

크로스체인 상호운용성은 DeFi 합성가능성에 필수적이지만, 현재 브릿지 설계는 심각한 문제에 직면해 있습니다:

- **신뢰 가정**: 대부분의 브릿지는 멀티시그 위원회나 신뢰받는 검증자에 의존하여 중앙화 위험과 단일 실패 지점을 만듭니다
- **전체 노드 요구사항**: 무신뢰 검증은 전통적으로 연결된 각 체인에 대한 전체 노드를 실행해야 하는데, 이는 비용이 많이 들고 비실용적입니다
- **최종성 지연**: 보안을 보장하기 위해 깊은 확인을 기다리면 사용자 경험이 나빠집니다
- **브릿지 공격**: 2022-2023년에 20억 달러 이상이 브릿지 해킹으로 손실되었으며, 주로 신뢰받는 중개자의 실패 때문입니다

ZK 라이트 클라이언트는 블록체인 합의를 검증하는 영지식 증명을 사용하여 이러한 문제를 해결합니다. 라이트 클라이언트는 모든 거래를 처리하거나 전체 상태를 저장하지 않고도 합의 규칙이 따라졌다는 증명을 확인하여 블록 헤더가 유효한지 검증할 수 있습니다.

ZK-DEX의 경우, 이를 통해:
- 다른 체인으로부터의 무신뢰 예치
- 금액을 노출하지 않는 프라이빗 크로스체인 전송
- 프라이버시 보존과 함께 원자적 크로스체인 스왑

## 기술 사양

### 아키텍처 개요

```
Source Chain                    Bridge Infrastructure                 ZK-DEX Chain
+------------+                  +------------------+                  +------------+
|            |   Headers        |                  |    ZK Proof      |            |
| Blockchain | --------------> | Header Relayer   | --------------> | Light      |
|   Node     |                  |                  |                  | Client     |
+------------+                  +------------------+                  | Contract   |
      |                                |                              +------------+
      |                         +------------------+                        |
      |  Consensus Data         |                  |                        |
      +----------------------> | Proof Generator  |                        |
                               | (Off-chain)      |                        |
                               +------------------+                        |
                                                                           v
                                                               +------------------+
                                                               | Deposit/Bridge   |
                                                               | Contract         |
                                                               +------------------+
```

### 구성 요소 목록

| 구성 요소 | 설명 |
|-----------|-------------|
| **Header Relayer** | 소스 체인을 모니터링하고 헤더와 합의 데이터를 증명 생성기에 제출 |
| **Proof Generator** | 합의 유효성에 대한 ZK 증명을 생성하는 오프체인 서비스 |
| **Light Client Contract** | 검증된 헤더 체인을 유지하는 온체인 검증자 |
| **Bridge Contract** | 검증된 헤더를 기반으로 예치/인출 처리 |
| **Consensus Circuit** | 소스 체인 합의 규칙을 증명하는 ZK 회로 |

### 데이터 흐름

1. **헤더 제출 흐름**
   - 릴레이어가 소스 체인에서 최신 최종화된 블록 헤더를 가져옵니다
   - 합의 데이터(검증자 서명, 증명) 수집
   - 증명 생성기가 헤더 유효성에 대한 ZK 증명 생성
   - 증명이 라이트 클라이언트 컨트랙트에 제출되어 검증

2. **예치 검증 흐름**
   - 사용자가 소스 체인에 자산을 예치
   - 예치 거래에 대한 머클 증명 생성
   - 헤더 유효성 + 거래 포함을 결합한 ZK 증명 생성
   - 증명 검증 시 ZK-DEX가 프라이빗 노트를 발행

### 합의 증명 유형

| 소스 체인 유형 | 증명 전략 |
|-------------------|----------------|
| **PoW (Ethereum pre-merge)** | 누적 난이도, 헤더 체인 연결 증명 |
| **PoS (Ethereum)** | 동기화 위원회 서명, BLS 집계 증명 |
| **Tendermint (Cosmos)** | 커밋에 대한 2/3+ 검증자 서명 증명 |
| **Nakamoto (Bitcoin)** | 충분한 작업 증명을 가진 헤더 체인 증명 |

## 효과

| 측면 | 영향 |
|--------|--------|
| **신뢰 모델** | 신뢰받는 중개자 의존성 제거; 보안은 소스 체인과 동일 |
| **자본 효율성** | 과잉 담보 불필요; 직접 1:1 자산 브릿지 |
| **프라이버시** | 브릿지 금액을 커밋먼트 스킴으로 숨길 수 있음 |
| **지연 시간** | 단일 최종화된 블록 후 검증 가능 (깊은 확인 대기 불필요) |
| **가스 비용** | 증명 검증당 약 300K-500K gas; 배치를 통해 분할 상환 |
| **탈중앙화** | 누구나 릴레이어 실행 가능; 허가된 검증자 세트 없음 |

## 보안 고려사항

| 위험 | 완화책 |
|------|------------|
| **회로 버그** | 합의 회로의 형식 검증; 다중 감사 라운드 |
| **재조직 공격** | 충분한 최종성 대기; 경제적 최종성 임계값 |
| **헤더 보류** | 다중 독립 릴레이어; 인센티브화된 제출 |
| **증명 가변성** | 구속력 있는 커밋먼트 스킴 사용; 증명 고유성 검증 |
| **장거리 공격 (PoS)** | 사회적 합의 체크포인트; 약한 주관성 경계 |
| **그리핑 공격** | 릴레이어 본드 요구; 잘못된 제출에 대한 슬래싱 |

## 구현 과제

1. **합의 회로 복잡성**
   - Ethereum PoS 동기화 위원회 검증은 BLS 서명 집계가 필요합니다
   - BLS12-381 페어링 연산은 회로에서 비용이 많이 듭니다 (~수백만 제약조건)
   - 사용자 정의 게이트가 있는 Halo2와 같은 특수 증명 시스템 사용 고려

2. **크로스체인 최종성 의미**
   - 다른 체인은 다른 최종성 보장을 가집니다
   - 소스의 "최종" → 목적지의 "검증됨"에 대한 명확한 매핑 필요
   - 확률적 vs. 결정적 최종성 모델 고려

3. **증명 생성 지연**
   - 합의 증명은 생성하는 데 몇 분에서 몇 시간이 걸릴 수 있습니다
   - 실시간 브릿지는 분쟁 기간이 있는 낙관적 모드가 필요합니다
   - 중복성과 속도를 위해 증명자 네트워크 필요

4. **헤더 동기화**
   - 라이트 클라이언트는 간격 없이 헤더 체인을 추적해야 합니다
   - 다운타임 후 따라잡기는 이전 헤더 증명이 필요합니다
   - 더 빠른 동기화를 위해 체크포인트 시스템 고려

5. **멀티체인 확장**
   - 각 소스 체인은 특수 합의 회로가 필요합니다
   - 검증 비용은 연결된 체인 수에 비례하여 증가합니다
   - 집계된 멀티체인 증명으로 비용 분할 상환 가능

## 파생물

1. **멀티체인 라이트 클라이언트** - 통합 증명 형식을 사용하여 여러 소스 체인의 헤더를 검증하는 단일 컨트랙트. 배포 오버헤드를 줄이고 원자적 멀티체인 작업을 가능하게 합니다. 합의 차이를 공통 인터페이스로 추상화해야 합니다.

2. **사기 증명 폴백** - 헤더가 챌린지 기간과 함께 낙관적으로 승인되는 하이브리드 모드. 일반적인 경우의 지연 시간을 줄이면서 사기 증명을 통해 보안을 유지합니다. 분쟁 중 주문형으로 ZK 증명 생성.

3. **빠른 최종성 브릿지** - 스테이킹된 검증자가 지원하는 즉각적인 브릿지를 제공하는 사전 확인 네트워크. ZK 라이트 클라이언트가 최종 상태를 정산; 사전 확인이 UX 제공. 슬래싱이 빠른 경로의 경제적 보안을 보장합니다.

4. **양방향 브릿지** - 두 체인 모두 서로의 라이트 클라이언트를 실행하는 완전한 양방향 브릿지. 비대칭 신뢰 없이 대칭적 작업을 가능하게 합니다. 소스 체인에 라이트 클라이언트 배포 필요.

5. **라이트 클라이언트 집계** - 여러 독립 라이트 클라이언트 구현이 동일한 헤더를 검증. 구현 간 합의가 심층 방어를 제공합니다. 다른 증명 시스템이 공통 모드 실패를 줄입니다.

## 사용 사례

1. **무신뢰 ETH 브릿지**
   - 사용자가 브릿지 운영자를 신뢰하지 않고 ZK-DEX에서 ETH를 거래하고 싶어합니다
   - Ethereum 메인넷의 브릿지 컨트랙트에 ETH를 예치
   - ZK 라이트 클라이언트가 예치를 포함하는 Ethereum 헤더를 검증
   - ZK-DEX에서 프라이빗 zkETH 노트 발행
   - 사용자는 완전한 Ethereum 보안 보장으로 거래

2. **크로스체인 차익거래**
   - Ethereum DEX와 ZK-DEX 간 가격 차이
   - 차익거래자가 라이트 클라이언트를 사용하여 무신뢰로 자산 브릿지
   - 양쪽에서 프라이빗하게 거래 실행
   - 이익을 다시 브릿지; 모든 이동이 ZK 증명으로 검증
   - 신뢰받는 당사자가 선행거래하거나 검열할 수 없음

3. **멀티체인 포트폴리오**
   - 기관 사용자가 Ethereum, Polygon, ZK-DEX에 자산 보유
   - 라이트 클라이언트가 모든 포지션의 검증된 뷰 제공
   - 크로스체인 재조정이 원자적으로 실행
   - 모든 체인의 무신뢰 검증이 있는 단일 인터페이스

4. **DeFi 합성가능성**
   - ZK-DEX의 프로토콜이 Ethereum 가격 피드가 필요
   - 라이트 클라이언트가 Chainlink 가격을 포함한 Ethereum 상태 검증
   - 오라클 데이터가 증명 가능하게 신선하고 진정성 있음
   - 투명한 체인 데이터로 프라이빗 DeFi 가능
