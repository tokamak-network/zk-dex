# H4. 크로스체인 메시징

암호화된 메시지 전달 및 프라이빗 크로스체인 작업을 가능하게 하는 프라이버시 보존 블록체인 간 통신 프로토콜입니다.

**요구사항**: 메시지 릴레이 인프라 | 암호화 스킴 | 메시지 진위성 ZK 증명 | 순서 보장

---

## 배경

크로스체인 메시징은 멀티체인 DeFi 조합성의 기초이지만, 현재 솔루션은 프라이버시가 부족합니다:

- **메시지 투명성**: 기존 프로토콜(LayerZero, Axelar, Wormhole)은 평문으로 메시지 전송
- **메타데이터 유출**: 콘텐츠 없이도 메시지 패턴이 애플리케이션 동작을 드러냄
- **중앙화된 릴레이어**: 대부분의 메시징이 허가형 릴레이어 네트워크에 의존
- **순서 취약점**: 메시지 순서 변경이 MEV 추출에 악용될 수 있음

프라이빗 크로스체인 메시징은 다음을 가능하게 합니다:
- 의도된 수신자만 읽을 수 있는 암호화된 페이로드
- 발신자, 수신자, 메시지 패턴을 숨기는 메타데이터 보호
- 암호화 검증을 통한 탈중앙화 릴레이
- 정보 유출 없는 원자적 멀티체인 작업

ZK-DEX에서는 외부 프로토콜 및 체인과의 프라이빗 조정을 가능하게 합니다.

## 기술 사양

### 아키텍처 개요

```
소스 체인                    릴레이 네트워크                    목적지 체인
+----------------+              +----------------+               +----------------+
|                |              |                |               |                |
|  Application   |  암호화된    |   Relayer 1    |   암호화된    |  Application   |
|       |        |   메시지     |   Relayer 2    |   메시지      |       |        |
|       v        |              |   Relayer 3    |               |       v        |
|  +---------+   |   +-----+    |       |        |    +-----+    |  +---------+   |
|  | Outbox  |----->| Enc |---->|       v        |--->| Dec |---->|  | Inbox   |   |
|  +---------+   |   +-----+    |   Aggregator   |    +-----+    |  +---------+   |
|                |              |       |        |               |       |        |
+----------------+              |       v        |               |       v        |
                                |  +---------+   |               |  +---------+   |
                                |  | ZK Proof|   |               |  | Verify  |   |
                                |  | of Auth |   |               |  | & Exec  |   |
                                |  +---------+   |               |  +---------+   |
                                +----------------+               +----------------+
```

### 구성 요소 목록

| 구성 요소 | 설명 |
|-----------|-------------|
| **Outbox Contract** | 릴레이를 위해 암호화된 메시지 대기열 관리 |
| **Encryption Module** | 수신자의 키로 페이로드 암호화 |
| **Relayer Network** | 탈중앙화 메시지 전송 계층 |
| **Aggregator** | 메시지를 배치하고 전달 증명 생성 |
| **Inbox Contract** | 목적지에서 메시지 수신 및 검증 |
| **ZK Auth Circuit** | 콘텐츠 공개 없이 메시지 진위성 증명 |

### 데이터 흐름

1. **메시지 전송**
   - 애플리케이션이 수신자의 공개키로 페이로드 암호화
   - 암호화된 메시지가 메타데이터 commitment와 함께 Outbox에 커밋
   - 릴레이어 네트워크가 대기 중인 메시지 수집
   - 효율적인 전달을 위해 메시지 배치 처리

2. **메시지 전달**
   - Aggregator가 메시지 배치의 유효성에 대한 ZK 증명 생성
   - 증명에는 다음 포함: 소스 체인 검증, 순서, 변조 없음
   - Inbox 컨트랙트가 증명을 검증하고 메시지 커밋
   - 수신자가 복호화하고 처리 가능

3. **프라이빗 콜백 흐름**
   - 체인 A에서 크로스체인 작업 시작
   - 결과가 암호화된 메시지를 통해 반환
   - 원래 발신자가 콜백 진위성 검증
   - 프라이빗하게 원자적 작업 완료

### 메시지 인증 회로

```circom
pragma circom 2.1.0;

include "../utils/poseidon/poseidon.circom";
include "../utils/ecdsa/verify.circom";

template MessageAuth() {
    // 공개 입력
    signal input messageCommitment;   // 암호화된 메시지의 해시
    signal input sourceChainId;       // 출처 체인
    signal input sequenceNumber;      // 순서 지정용
    signal input deliveryCommitment;  // 전달 파라미터에 대한 commitment

    // 프라이빗 입력
    signal input encryptedPayload[32]; // 암호화된 메시지 콘텐츠
    signal input senderPk;             // 발신자 공개키 (숨김)
    signal input receiverPk;           // 수신자 공개키 (숨김)
    signal input nonce;                // 암호화 nonce
    signal input timestamp;            // 메시지 타임스탬프
    signal input signature[2];         // 발신자의 서명

    // 메시지 commitment 검증
    component msgHash = Poseidon(34);
    for (var i = 0; i < 32; i++) {
        msgHash.inputs[i] <== encryptedPayload[i];
    }
    msgHash.inputs[32] <== nonce;
    msgHash.inputs[33] <== timestamp;
    msgHash.out === messageCommitment;

    // 전달 commitment가 발신자/수신자를 숨김 검증
    component deliveryHash = Poseidon(3);
    deliveryHash.inputs[0] <== senderPk;
    deliveryHash.inputs[1] <== receiverPk;
    deliveryHash.inputs[2] <== sequenceNumber;
    deliveryHash.out === deliveryCommitment;

    // 서명 검증은 여기에 위치
    // (예시를 위해 단순화)
}

component main {public [messageCommitment, sourceChainId, sequenceNumber, deliveryCommitment]} = MessageAuth();
```

## 효과

| 측면 | 영향 |
|--------|--------|
| **페이로드 프라이버시** | 메시지 콘텐츠 암호화; 수신자만 읽기 가능 |
| **메타데이터 프라이버시** | commitment를 통해 발신자/수신자 숨김 |
| **패턴 보호** | 메시지 배치 처리로 통신 패턴 모호화 |
| **검열 저항성** | 탈중앙화 릴레이어; 단일 병목 지점 없음 |
| **순서 보장** | 시퀀스 번호로 순서 변경 공격 방지 |
| **조합성** | 프라이빗 멀티체인 DeFi 작업 가능 |

## 보안 고려사항

| 위험 | 완화 방법 |
|------|------------|
| **릴레이 검열** | 독립적인 여러 릴레이어; 인센티브 정렬 |
| **메시지 변조** | 암호화 commitment; 서명 검증 |
| **재생 공격** | 시퀀스 번호; nonce 추적 |
| **타이밍 분석** | 메시지 배치 처리; 무작위 지연 |
| **키 손상** | 전방향 비밀성; 키 회전 프로토콜 |
| **순서 조작** | 엄격한 시퀀스 강제; 사기 증명 |

## 구현 과제

1. **종단간 암호화**
   - 크로스체인 참여자를 위한 키 교환 프로토콜 필요
   - 중앙화된 레지스트리 없이 공개키 발견
   - 온체인 키 commitment 사용 고려

2. **지연 vs. 프라이버시 트레이드오프**
   - 배치 처리는 프라이버시를 개선하지만 지연 추가
   - 실시간 메시징은 타이밍 정보 유출 가능
   - 다양한 사용 사례를 위한 구성 가능한 프라이버시 레벨

3. **릴레이어 인센티브**
   - 대역폭과 가스에 대해 릴레이어에게 보상 필요
   - 수수료 메커니즘이 메시지 가치를 유출하지 않아야 함
   - 암호화된 수수료 commitment 고려

4. **메시지 순서**
   - 체인 간 인과 순서 지정은 복잡
   - 체인마다 다른 최종성 시간
   - 벡터 시계 또는 유사 메커니즘 필요

5. **대용량 메시지 처리**
   - 암호화 및 증명이 메시지 크기에 따라 확장
   - 대용량 페이로드에 청킹 필요할 수 있음
   - 온체인 commitment를 가진 오프체인 저장소 고려

## 파생 형태

1. **암호화 크로스체인** - 전방향 비밀성을 가진 전체 페이로드 암호화. 각 메시지가 임시 키 사용. 장기 키의 손상이 과거 메시지를 노출하지 않음.

2. **배치 메시징** - 여러 메시지를 단일 전달 증명으로 집계. 검증 비용 상각. 더 큰 익명 집합을 통해 프라이버시 개선.

3. **메시지 순서** - 체인 간 엄격한 인과 순서 보장. 메시지 시퀀스에 대한 의존성 추적. 상태를 가진 크로스체인 프로토콜에 필수.

4. **신뢰할 수 있는 전달** - 승인과 함께 보장된 메시지 전달. 실패 시 자동 재시도. 릴레이어 네트워크의 SLA commitment.

5. **크로스체인 콜백** - 체인 간 원자적 요청-응답 패턴. 체인 A의 작업이 체인 B의 액션을 트리거하고 결과 반환. 프라이빗 크로스체인 스마트 컨트랙트 조합 가능.

## 사용 사례

1. **프라이빗 크로스체인 거버넌스**
   - 이더리움의 DAO, ZK-DEX에서 실행
   - 투표 결과가 암호화된 메시지를 통해 전송
   - 외부 관찰자로부터 실행 세부사항 숨김
   - 실행될 때까지 거버넌스 액션 비공개

2. **크로스체인 주문 라우팅**
   - 사용자가 ZK-DEX에 주문 제출
   - 외부 DEX에서 더 나은 가격 발견
   - 암호화된 메시지가 크로스체인으로 주문 라우팅
   - 실행 및 라우팅 전략 숨김

3. **멀티체인 청산**
   - 체인 A의 담보, 체인 B의 부채
   - 프라이빗 메시지를 통해 건강도 모니터링
   - 체인 간 프라이빗하게 청산 조정
   - 전 과정에서 포지션 세부사항 숨김

4. **프라이빗 오라클 업데이트**
   - 여러 체인의 가격 피드
   - 암호화된 메시지를 통해 데이터 전송
   - ZK-DEX에서 프라이빗하게 집계
   - 외부 관찰자가 업데이트를 선행 거래할 수 없음

## 실제 제품 및 사용자 경험

### 1. "메타데이터 숨김 메시징" - 통신 패턴 비공개 서비스

**제품 설명**:
메시지 내용뿐 아니라 누가 누구에게, 언제, 얼마나 자주 통신하는지까지 숨기는 프라이버시 메시징. 일반 암호화 메시지는 내용만 숨기고 패턴은 노출됩니다.

**일반 사용자 경험**:
- 정민호씨(36세, 스타트업 대표)는 M&A 협상 중
- 일반 암호화: "민호씨가 특정 주소와 매일 통신" 패턴 노출
- 메타데이터 숨김: 통신 상대, 빈도, 타이밍 모두 비공개
- 외부 관찰자는 민호씨가 누구와 협상 중인지 알 수 없음
- M&A 상대방이 누구인지 발표 전까지 완전 비밀

**관찰 가능한 이점**:
- 비즈니스 관계 자체가 비공개
- 통신 패턴으로 거래 추론 방지
- "누구와 대화하는가"가 전략적 정보일 때 보호

### 2. "프라이빗 크로스체인 지시" - MEV 방지 거래 전달

**제품 설명**:
한 체인에서 다른 체인으로 거래 지시를 보낼 때, 릴레이어도 거래 내용을 알 수 없는 프라이버시 메시징.

**일반 사용자 경험**:
- 박소영씨(28세)는 이더리움 가격 조건 충족 시 ZK-DEX에서 자동 매수 설정
- 일반 크로스체인: 릴레이어가 거래 내용을 보고 MEV 추출 가능
- 프라이빗 메시징: 거래 지시가 암호화되어 전달
- 릴레이어는 "어떤 메시지가 있다"만 알고 내용은 모름
- ZK-DEX 컨트랙트만 복호화하여 실행

**관찰 가능한 이점**:
- 크로스체인 MEV로부터 완벽한 보호
- 자동화 전략이 릴레이어에게 노출되지 않음
- 크로스체인 조건부 주문의 프라이버시 확보

### 3. "익명 크로스체인 투표" - 투표자 신원 완전 비공개

**제품 설명**:
여러 체인에 걸친 거버넌스 투표에서 누가 어떻게 투표했는지 완전히 숨기면서 유효한 투표를 증명하는 서비스.

**일반 사용자 경험**:
- 이현수씨(45세)는 논쟁적인 DAO 제안에 반대 투표하고 싶음
- 일반 투표: "현수씨가 반대 투표" 공개 → 커뮤니티 압력 우려
- 익명 투표: 투표 자격만 ZK로 증명, 투표 내용은 암호화
- 집계 시 전체 결과만 공개, 개인 투표는 영원히 비밀
- 현수씨가 반대했는지 찬성했는지 아무도 모름

**관찰 가능한 이점**:
- 투표에 대한 사회적 압력/보복 방지
- 진정한 의사 표현 가능
- 대형 토큰 홀더의 영향력 행사 숨김
