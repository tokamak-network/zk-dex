# I2. RFQ 시스템

프라이버시 보존 온체인 정산과 함께 오프체인 협상을 통해 맞춤형 가격을 가능하게 하는 견적 요청 인프라.

**요구사항**: 암호화된 RFQ 브로드캐스트 | 딜러 견적 집계 | 최적 체결 선택 | ZK 정산 증명

---

## 배경

표준 주문장 거래는 많은 거래 유형에 비효율적입니다:

- **대규모 주문**: 시장가 주문은 과도한 슬리피지 발생; 지정가 주문은 의도 신호
- **이색 쌍**: 비유동 시장은 넓은 스프레드와 열악한 체결
- **맞춤 조건**: 비표준 정산, 부분 체결 또는 조건이 지원되지 않음
- **관계 가치**: 기관 거래자는 익명 시장에서 보이지 않는 딜러 관계를 중시

RFQ(견적 요청) 시스템은 다음을 통해 이를 해결합니다:
- 거래자가 여러 딜러로부터 맞춤형 견적을 요청할 수 있음
- 시장 메이커 간 최고 가격 경쟁 가능
- 공개 정보 유출 없이 협상 지원
- 최적 체결을 보장하면서 프라이버시 보존

ZK-DEX의 경우, RFQ는 프라이버시 보존 정산으로 정교한 거래를 가능하게 합니다.

## 기술 사양

### 아키텍처 개요

```
요청자                        RFQ 네트워크                       딜러
+--------+                    +------------------+               +--------+
|        |  암호화된 RFQ      |                  |  브로드캐스트 |        |
|거래자  |------------------>|  RFQ             |-------------->|딜러 1  |
|        |                    |  집계자          |               |        |
+--------+                    |                  |               +--------+
    ^                         |  +------------+  |               |        |
    |                         |  | 견적       |  |  견적         |딜러 2  |
    |                         |  | 수집기     |<----------------|        |
    |                         |  +------------+  |               +--------+
    |    최적 견적            |        |         |               |        |
    |<------------------------|        v         |  견적         |딜러 3  |
    |                         |  최적 체결       |<--------------|        |
    v                         |  선택            |               +--------+
+--------+                    +------------------+
|ZK-DEX  |  정산
|정산    |<------------------
+--------+
```

### 컴포넌트 목록

| 컴포넌트 | 설명 |
|-----------|-------------|
| **RFQ 브로드캐스터** | 암호화된 RFQ를 자격있는 딜러에게 배포 |
| **견적 집계자** | 딜러 견적을 수집하고 비교 |
| **최적 체결 엔진** | 기준에 따라 최적 견적 선택 |
| **견적 커밋먼트** | 제출 시 견적이 유효했다는 ZK 증명 |
| **정산 컨트랙트** | 견적 조건으로 거래 체결 |
| **딜러 레지스트리** | 승인된 시장 메이커 및 평판 추적 |

### 데이터 흐름

1. **RFQ 브로드캐스트**
   - 거래자가 RFQ 생성: 자산 쌍, 크기, 방향, 조건
   - RFQ가 승인된 딜러에게만 암호화됨
   - 딜러는 RFQ를 봄; 시장은 보지 못함

2. **견적 수집**
   - 딜러가 구속력 있는 견적으로 응답
   - 견적이 조건의 ZK 증명과 함께 커밋됨
   - 집계자가 시간 창 내 견적 수집

3. **선택 및 정산**
   - 거래자가 최적 견적 선택 (또는 자동 선택)
   - 선택된 견적이 정산을 위해 공개됨
   - 거래가 ZK-DEX에서 원자적으로 체결

### RFQ 프로토콜 회로

```circom
pragma circom 2.1.0;

include "../utils/poseidon/poseidon.circom";
include "../utils/signatures/eddsa.circom";

template RFQQuote() {
    // 공개 입력
    signal input quoteCommitment;    // 딜러 견적에 대한 커밋먼트
    signal input rfqHash;            // 원본 RFQ에 대한 참조
    signal input dealerCommitment;   // 숨겨진 딜러 신원
    signal input expiry;             // 견적 만료 시간

    // 비공개 입력
    signal input price;              // 견적 가격 (수락까지 숨김)
    signal input size;               // 최대 체결 가능 크기
    signal input dealerPk;           // 딜러 공개키
    signal input dealerSk;           // 딜러 서명 키
    signal input salt;               // 무작위성

    // 견적 커밋먼트 검증
    component quoteHash = Poseidon(5);
    quoteHash.inputs[0] <== price;
    quoteHash.inputs[1] <== size;
    quoteHash.inputs[2] <== rfqHash;
    quoteHash.inputs[3] <== expiry;
    quoteHash.inputs[4] <== salt;
    quoteHash.out === quoteCommitment;

    // 딜러 커밋먼트 검증
    component dealerHash = Poseidon(2);
    dealerHash.inputs[0] <== dealerPk;
    dealerHash.inputs[1] <== salt;
    dealerHash.out === dealerCommitment;

    // 구속력 있는 견적을 위한 서명 검증
    // (간소화 - 전체 EdDSA 검증이 여기 위치)
}

component main {public [quoteCommitment, rfqHash, dealerCommitment, expiry]} = RFQQuote();
```

## 효과

| 측면 | 영향 |
|--------|--------|
| **가격 발견** | 경쟁 견적이 공정한 시장 가격 공개 |
| **체결 품질** | N개 견적 중 최고가 최적 가격 보장 |
| **프라이버시** | RFQ 세부정보가 일반 시장에서 숨김 |
| **맞춤화** | 비표준 조건을 오프체인에서 협상 가능 |
| **시장 충격** | 거래 정산까지 유출 없음 |
| **딜러 경쟁** | 여러 견적이 좁은 스프레드 보장 |

## 보안 고려사항

| 위험 | 완화 |
|------|------------|
| **견적 쇼핑** | 견적은 구속력 있음; 미체결 시 페널티 |
| **정보 유출** | 암호화된 RFQ; 승인된 딜러만 |
| **Last Look 남용** | Last look 제거 또는 시간 제한 |
| **딜러 담합** | 평판 추적; 다양한 딜러 세트 |
| **견적 스터핑** | 속도 제한; 딜러 보증금 |
| **정산 실패** | 원자적 정산; 담보 요구사항 |

## 구현 과제

1. **딜러 승인**
   - 어떤 딜러가 RFQ를 받을까?
   - 경쟁과 정보 유출 간 균형
   - 평판 기반 계층화 고려

2. **견적 유효성**
   - RFQ 프로세스 중 시장이 움직임
   - 견적은 시간 제한이 있어야 함
   - 변동성 높은 시장을 위한 스트리밍 견적 고려

3. **Last Look 논란**
   - 딜러는 수락 후 거부 옵션을 원할 수 있음
   - 거래자 불이익; 남용 가능성
   - ZK 커밋먼트가 last look을 암호학적으로 제한

4. **부분 체결**
   - 딜러가 전체 크기를 갖지 못할 수 있음
   - 부분 체결 프로토콜 필요
   - 딜러 간 집계 고려

5. **지연 공정성**
   - 더 빠른 딜러가 RFQ를 먼저 봄
   - 공정한 배포 메커니즘 필요
   - RFQ의 배치 공개 고려

## 파생상품

1. **멀티 딜러 RFQ** - 여러 딜러로부터 동시 견적. 최고 가격이 자동으로 승리. 딜러는 서로의 견적을 보지 못함.

2. **스트리밍 견적** - 딜러가 지속적인 견적 업데이트 제공. 변동성 높은 시장을 위한 실시간 가격. 스프레드가 좁아질 때 자동 체결.

3. **Last Look** - 최종 체결 전 딜러 검토 옵션. 남용 방지를 위한 시간 제한. 요청자가 구성 가능 (스프레드에 영향).

4. **음성 거래 통합** - 전통적인 음성 협상과 하이브리드 RFQ. 복잡한 조건을 시스템 외부에서 논의. 프라이버시를 위해 ZK-DEX에서 정산.

5. **RFQ 집계** - 여러 작은 RFQ를 단일 딜러 쿼리로 결합. 규모 집계를 통한 더 나은 가격. 조정된 정산.

## 사용 사례

1. **대규모 블록 거래**
   - 거래자가 비유동 토큰 $500만 매수 필요
   - 주문장에 $50만 가시 유동성만 존재
   - 딜러 RFQ가 0.5% 프리미엄으로 $500만 발견
   - 다일 축적 대신 단일 체결

2. **맞춤 정산 조건**
   - 거래자가 즉시 정산 대신 T+2 정산 원함
   - 표준 DEX는 지연 정산 미지원
   - RFQ가 딜러와 조건 협상
   - 정산 컨트랙트가 합의된 조건 집행

3. **교차 자산 패키지**
   - 펀드 리밸런싱이 A 매도 및 B 매수 필요
   - 슬리피지 방지를 위해 패키지에 대한 단일 견적 원함
   - 딜러가 결합 거래에 대한 스프레드 견적
   - 양측의 원자적 체결

4. **비유동 시장 메이킹**
   - 주문장 유동성이 없는 신규 토큰
   - 거래자가 RFQ를 사용하여 거래 상대방 발견
   - 딜러가 지속적인 견적 없이 유동성 제공
   - 양자 거래를 통해 시장 발전

## 실제 제품 및 사용자 경험

### 1. "비공개 견적 요청" - 딜러에게도 신원 숨김

**제품 설명**:
RFQ를 보낼 때 요청자의 신원이 딜러에게도 공개되지 않는 완전 익명 견적 시스템. 딜러는 "누가 요청했는지" 모른 채 견적만 제시합니다.

**일반 사용자 경험**:
- 정수민씨(45세)는 $30만 USDC 환전 필요
- 일반 RFQ: 딜러가 "정씨가 대량 환전 요청" 파악 → 정보 축적
- 비공개 RFQ: 딜러는 "익명이 $30만 환전 요청"만 봄
- 견적 제출 후 체결되어도 딜러는 고객 신원 모름
- 정씨의 거래 빈도, 규모 패턴이 딜러에게 축적되지 않음

**관찰 가능한 이점**:
- 딜러의 고객 정보 수집 차단
- 거래 이력 기반 가격 차별 방지
- 매번 동등한 조건으로 견적 수신

### 2. "견적 내용 비공개" - 선택 안 된 견적 영구 비밀

**제품 설명**:
여러 딜러 견적 중 선택되지 않은 견적은 절대 공개되지 않아 딜러의 가격 전략이 보호되는 프라이버시 RFQ.

**일반 사용자 경험**:
- 박회장(60세)이 $1,000만 BTC 매입 RFQ 발송
- 딜러 A: $60,100, 딜러 B: $60,050, 딜러 C: $60,150 견적
- 딜러 B 선택, 체결
- 딜러 A, C는 "내 견적이 선택 안 됐다"만 알고 다른 견적 모름
- 경쟁 딜러의 가격 전략이 서로에게 노출되지 않음

**관찰 가능한 이점**:
- 딜러 간 가격 담합 방지
- 딜러의 독자적 가격 책정 전략 보호
- 더 공정한 경쟁 견적 유도

### 3. "거래 이력 격리" - 연속 RFQ 간 연결 차단

**제품 설명**:
같은 사용자의 연속된 RFQ 요청이 서로 연결되지 않아 "이 사람이 지속적으로 매집 중"이라는 패턴 분석을 차단하는 서비스.

**일반 사용자 경험**:
- 투자사가 일주일에 걸쳐 5번의 대량 매수 RFQ 발송
- 일반 RFQ: 딜러가 "이 고객이 매집 중" 파악 → 가격 조정
- 이력 격리 RFQ: 각 요청이 완전히 독립적으로 처리
- 딜러는 5개 요청이 같은 주체인지 알 수 없음
- 대량 포지션 구축 전략이 딜러에게 노출되지 않음

**관찰 가능한 이점**:
- 연속 거래 의도 추론 방지
- 매집/분배 전략 비공개
- 공정한 가격 유지 (정보 비대칭 제거)
