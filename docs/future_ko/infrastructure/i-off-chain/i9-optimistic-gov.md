# I9. 낙관적 거버넌스

이의가 제기되지 않는 한 제안이 자동으로 실행되어 논란 없는 결정에 대한 오버헤드를 줄이는 거버넌스 메커니즘.

**요구사항**: 이의 제기 메커니즘 | 타임락 윈도우 | 가디언 시스템 | 에스컬레이션 절차

---

## 배경

전통적인 거버넌스는 상당한 마찰이 있습니다:

- **투표 오버헤드**: 모든 제안이 적극적인 참여를 요구
- **결정 지연**: 정족수를 기다리는 것이 일상적인 변경을 지연
- **투표자 피로**: 지속적인 투표가 참여 저하로 이어짐
- **기회 비용**: 명백한 결정에 투표하는 데 시간을 소비

낙관적 거버넌스는 다음을 통해 이를 해결합니다:
- 이의가 제기되지 않는 한 제안이 통과된다고 가정
- 적극적인 승인보다 적극적인 반대 요구
- 논란 없는 변경의 빠른 실행 가능
- 논쟁적인 결정에 대한 완전한 심의 보존

ZK-DEX의 경우, 이것은 이의 제기 메커니즘을 통해 보안을 유지하면서 효율적인 거버넌스를 가능하게 합니다.

### 구성 요소 목록

| 구성 요소 | 설명 |
|-----------|-------------|
| **Proposal Queue** | 이의 제기 윈도우 동안 제안 보관 |
| **Challenge Contract** | 이의 제기 수락 및 검증 |
| **Timer Oracle** | 이의 제기 윈도우 만료 추적 |
| **Escalation Engine** | 이의 제기된 제안을 전체 투표로 라우팅 |
| **Guardian System** | 보안 이슈에 대한 권한 있는 이의 제기자 |
| **Execution Module** | 통과된 제안을 자동으로 실행 |

### 데이터 흐름

1. **제안 제출**
   - 제안자가 보증금과 함께 제출
   - 이의 제기 윈도우 시작 (예: 7일)
   - 모든 이해관계자에게 제안 표시

2. **이의 제기 윈도우**
   - 이의 제기 없음: 실행을 위해 제안 대기열에 추가
   - 이의 제기: 전체 거버넌스 투표로 에스컬레이션
   - 이의 제기자는 보증금을 스테이크해야 함

3. **해결**
   - 이의 제기 없음: 윈도우 후 자동 실행
   - 이의 제기 + 투표 통과: 실행; 이의 제기자 슬래싱
   - 이의 제기 + 투표 실패: 거부; 제안자 슬래싱

### 낙관적 거버넌스 회로

```circom
pragma circom 2.1.0;

include "../utils/poseidon/poseidon.circom";
include "../utils/comparators.circom";

template OptimisticChallenge() {
    // Public inputs
    signal input proposalHash;        // Hash of proposal
    signal input challengeCommitment; // Commitment to challenge
    signal input windowEnd;           // Challenge window end time
    signal input currentTime;         // Current timestamp

    // Private inputs
    signal input challenger;          // Challenger identity (hidden)
    signal input challengeBond;       // Bond amount
    signal input reason;              // Challenge reason code
    signal input salt;

    // Verify challenge commitment
    component chalHash = Poseidon(5);
    chalHash.inputs[0] <== proposalHash;
    chalHash.inputs[1] <== challenger;
    chalHash.inputs[2] <== challengeBond;
    chalHash.inputs[3] <== reason;
    chalHash.inputs[4] <== salt;
    chalHash.out === challengeCommitment;

    // Verify challenge within window
    component timeCheck = LessThan(64);
    timeCheck.in[0] <== currentTime;
    timeCheck.in[1] <== windowEnd;
    timeCheck.out === 1;

    // Verify minimum bond
    component bondCheck = GreaterEqThan(64);
    bondCheck.in[0] <== challengeBond;
    bondCheck.in[1] <== 1000;  // Minimum bond
    bondCheck.out === 1;
}

component main {public [proposalHash, challengeCommitment, windowEnd, currentTime]} = OptimisticChallenge();
```

## 영향

| 측면 | 영향 |
|--------|--------|
| **효율성** | 논란 없는 제안이 투표 없이 실행 |
| **지연 시간** | 일상적인 변경의 더 빠른 실행 |
| **참여** | 논쟁적인 이슈만 적극적인 투표 필요 |
| **보안** | 이의 제기 메커니즘이 나쁜 제안 방지 |
| **비용 절감** | 일상적인 거버넌스에 더 적은 가스 소비 |
| **관심 배분** | 중요한 제안에 집중 |

## 보안 고려사항

| 위험 | 완화 |
|------|------------|
| **악의적인 제안** | 보증금 요구사항; 가디언 감독 |
| **이의 제기 그리핑** | 이의 제기자 보증금; 경솔한 이의 제기에 대한 슬래싱 |
| **시간대 공격** | 긴 이의 제기 윈도우; 글로벌 알림 |
| **담합** | 여러 가디언 클래스; 커뮤니티 감독 |
| **긴급 우회** | 긴급 일시 중지 기능; 보안 위원회 |
| **제안 스팸** | 빈번한 제안자에 대한 보증금 증가 |

## 구현 과제

1. **윈도우 기간**
   - 너무 짧음: 불충분한 검토 시간
   - 너무 길음: 불필요한 지연
   - 제안 유형별 윈도우 고려

2. **보증금 조정**
   - 너무 낮음: 스팸과 그리핑
   - 너무 높음: 참여 장벽
   - 제안 영향에 따른 동적 보증금

3. **가디언 선택**
   - 누가 이의를 제기할 수 있는가?
   - 접근성과 스팸 방지 간 균형
   - 계층화된 이의 제기 권한 고려

4. **알림 시스템**
   - 이해관계자가 제안을 알아야 함
   - 모르는 것에 이의를 제기할 수 없음
   - 다중 채널 알림 필수

5. **긴급 절차**
   - 일부 결정은 윈도우를 기다릴 수 없음
   - 안전장치가 있는 긴급 고속 트랙 필요
   - 긴급 상태에 대한 명확한 기준

## 파생물

1. **Challenge Period** - 다양한 제안 유형에 대한 구성 가능한 윈도우. 보안 변경: 14일. 매개변수 조정: 3일. 긴급성 기반 가속.

2. **Guardian Systems** - 향상된 이의 제기 권한이 있는 지정 엔티티. 보안 위원회, 핵심 팀, 선출된 대표. 다양한 관심사에 대한 여러 가디언 클래스.

3. **Escalation Procedures** - 이의 제기에서 해결까지의 명확한 경로. 각 단계에 대한 정의된 타임라인. 조치가 없으면 자동 진행.

4. **Time-Locked Execution** - 윈도우 후에도 실행 지연. 추가 안전 버퍼. 최후의 수단 개입 허용.

5. **Emergency Vetoes** - 중요한 이슈에 대한 고속 트랙 거부. 높은 평판의 이의 제기자 필요. 즉시 일시 중지; 확인을 위한 투표.

## 사용 사례

1. **일상적인 매개변수 업데이트**
   - 제안: 오라클 주소를 새 버전으로 업데이트
   - 낮은 위험, 잘 이해된 변경
   - 윈도우 동안 이의 제기 없음
   - 7일 후 자동 실행

2. **논란 있는 재무 지출**
   - 제안: 대규모 마케팅 지출
   - 커뮤니티 멤버가 이의 제기
   - 전체 거버넌스 투표 트리거
   - 논쟁적인 이슈에 대한 심의

3. **긴급 보안 패치**
   - 중요한 취약점 발견
   - 가디언이 긴급 트랙 호출
   - 단축된 윈도우 (24시간)
   - 감독과 함께 빠른 실행

4. **악의적인 제안 차단**
   - 공격자가 해로운 제안 제출
   - 가디언이 즉시 이의 제기
   - 전체 투표가 제안 거부
   - 제안자 보증금 슬래싱

## 실제 제품 및 사용자 경험

### 1. "익명 챌린지" - 챌린저 신원 보호

**제품 설명**:
제안에 챌린지할 때 챌린저의 신원이 공개되지 않아 보복 두려움 없이 문제 제기를 할 수 있는 프라이버시 챌린지 시스템.

**일반 사용자 경험**:
- 이슈를 발견했지만 제안자가 영향력 있는 인물
- 일반 챌린지: "김씨가 대표님 제안에 챌린지" → 정치적 갈등
- 익명 챌린지: 챌린저 신원이 ZK로 숨겨짐
- "유효한 챌린지가 제출됨"만 공개, 누가 했는지는 비밀
- 챌린지 이유와 본드만 검증됨

**관찰 가능한 이점**:
- 권력자 제안에도 자유롭게 문제 제기
- 정치적 보복 두려움 제거
- 솔직한 거버넌스 감시 가능

### 2. "비공개 감시 활동" - 가디언 모니터링 숨김

**제품 설명**:
가디언이 어떤 제안을 모니터링하고 있는지가 공개되지 않아 "가디언이 안 보고 있을 때" 공격을 방지하는 프라이버시 감시 시스템.

**일반 사용자 경험 (가디언 관점)**:
- 가디언 박씨는 모든 제안을 검토
- 일반 감시: "가디언 A가 제안 1, 3을 봄" → 2, 4는 취약
- 비공개 감시: 가디언 활동 내역이 숨겨짐
- 공격자는 "어느 제안이 감시 중인지" 알 수 없음
- 모든 제안이 잠재적으로 감시되는 것처럼 보임

**관찰 가능한 이점**:
- 감시 공백 추론 방지
- 공격자의 타이밍 게임 차단
- 전체 제안에 대한 억제 효과

### 3. "긴급 제안자 보호" - 취약점 보고자 익명성

**제품 설명**:
보안 취약점을 발견하고 긴급 제안을 제출할 때 제안자의 신원이 보호되어 "누가 취약점을 발견했는지" 추적이 불가능한 시스템.

**일반 사용자 경험**:
- 화이트햇 해커가 심각한 취약점 발견
- 일반 긴급 제안: "이 해커가 취약점 발견" → 타겟 우려
- 익명 긴급 제안: ZK 증명으로 유효성만 검증
- 취약점 내용과 수정 방법만 공개, 발견자는 숨김
- 보상은 프라이빗 채널로 지급

**관찰 가능한 이점**:
- 보안 연구자의 신원 보호
- 취약점 보고 인센티브 강화
- 보복 공격 우려 제거
