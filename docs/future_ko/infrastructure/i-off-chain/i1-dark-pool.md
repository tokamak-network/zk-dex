# I1. 다크풀 매칭

정보 유출 없이 대규모 거래를 가능하게 하는 보안 다자간 연산(MPC)을 활용한 프라이버시 보존 주문 매칭 엔진.

**요구사항**: MPC 인프라 | 암호화된 주문 제출 | 임계값 복호화 | 정산 통합

---

## 배경

대규모 주문은 투명한 시장에서 심각한 체결 문제에 직면합니다:

- **시장 충격**: 눈에 보이는 대규모 주문은 체결 전 거래자에게 불리한 방향으로 가격을 움직입니다
- **선행매매**: MEV 추출자가 감지된 대규모 거래를 복사하거나 선행매매합니다
- **정보 유출**: 주문 흐름이 경쟁자에게 거래 의도를 드러냅니다
- **약탈적 거래**: 정교한 행위자가 예측 가능한 대규모 주문 행동을 악용합니다

다크풀은 다음을 통해 이러한 문제를 해결합니다:
- 매칭 후까지 주문 세부정보 숨기기
- 개별 의도를 공개하지 않고 주문 매칭
- 공정성을 보장하기 위해 중간시장 가격에서 체결
- 정보 기반 거래 이점 방지

ZK-DEX의 경우, 다크풀 매칭은 대규모 주문에 대한 기관급 체결을 가능하게 합니다.

## 기술 사양

### 아키텍처 개요

```
거래자                        MPC 매칭 엔진                정산
+--------+                     +------------------------+         +---------+
|        |  암호화된 주문      |                        |         |         |
|거래자 A|-------------------->|  MPC 노드 1            |         | ZK-DEX  |
|        |                     |  MPC 노드 2            |  매칭   | 스마트  |
+--------+                     |  MPC 노드 3            |-------->|컨트랙트 |
|        |  암호화된 주문      |         |              |         |         |
|거래자 B|-------------------->|         v              |         +---------+
|        |                     |  +----------------+    |
+--------+                     |  | 보안 매칭      |    |
                               |  | 연산           |    |
                               |  +----------------+    |
                               |         |              |
                               |         v              |
                               |  매칭 결과             |
                               |  (주문 세부정보 없음)  |
                               +------------------------+
```

### 컴포넌트 목록

| 컴포넌트 | 설명 |
|-----------|-------------|
| **주문 암호화** | MPC 임계값 복호화를 위해 주문 암호화 |
| **MPC 노드** | 보안 매칭 연산을 수행하는 분산 노드 |
| **매칭 프로토콜** | 암호화된 주문에 대한 가격-시간 우선순위 매칭 |
| **정산 브리지** | 매칭된 주문을 ZK-DEX에 연결하여 체결 |
| **공정성 검증자** | 매칭이 명시된 규칙을 따랐는지 확인 |
| **감사 추적** | 규정 준수를 위한 프라이버시 보존 기록 |

### 데이터 흐름

1. **주문 제출**
   - 거래자가 임계값 암호화로 주문(가격, 수량, 방향)을 암호화
   - 암호화된 주문을 MPC 네트워크에 제출
   - 주문 확인; 거래자가 커밋먼트를 수신

2. **매칭 단계**
   - MPC 노드가 공동으로 주문 매칭 연산
   - 단일 노드도 주문 세부정보를 알 수 없음
   - 교차되지 않은 주문을 공개하지 않고 교차된 주문 식별

3. **정산 단계**
   - 매칭된 주문을 정산을 위해 복호화
   - 매칭되지 않은 주문은 암호화 상태 유지
   - ZK-DEX가 거래를 원자적으로 정산

### MPC 매칭 프로토콜

```
프로토콜: 보안 주문 매칭 (간소화)

설정:
- N개 MPC 노드, 임계값 T (예: 5개 중 3개)
- 각 주문이 임계값 스킴으로 암호화됨

매칭 라운드:
1. 각 노드가 암호화된 주문의 공유를 수신
2. 노드들이 공동으로 교차 로직 연산:
   - 매수 주문을 가격 내림차순으로 정렬
   - 매도 주문을 가격 오름차순으로 정렬
   - 교차 지점 찾기
3. 출력: 매칭된 쌍 목록 (미매칭 가격은 공개 안 됨)

보안 속성:
- T-1개 공모 노드는 아무것도 알 수 없음
- 매칭된 주문은 거래 상대방에게만 공개됨
- 미매칭 주문은 완전히 비공개로 유지
```

### 주문 커밋먼트 회로

```circom
pragma circom 2.1.0;

include "../utils/poseidon/poseidon.circom";

template DarkPoolOrder() {
    // 공개 입력
    signal input orderCommitment;    // 주문에 대한 커밋먼트
    signal input nullifier;          // 이중 제출 방지
    signal input traderCommitment;   // 숨겨진 거래자 신원

    // 비공개 입력
    signal input price;              // 지정가 (숨김)
    signal input amount;             // 주문 수량 (숨김)
    signal input side;               // 매수(1) 또는 매도(0)
    signal input traderPk;           // 거래자 공개키
    signal input salt;               // 무작위성

    // 주문 커밋먼트 검증
    component orderHash = Poseidon(5);
    orderHash.inputs[0] <== price;
    orderHash.inputs[1] <== amount;
    orderHash.inputs[2] <== side;
    orderHash.inputs[3] <== traderPk;
    orderHash.inputs[4] <== salt;
    orderHash.out === orderCommitment;

    // 거래자 커밋먼트 검증
    component traderHash = Poseidon(2);
    traderHash.inputs[0] <== traderPk;
    traderHash.inputs[1] <== salt;
    traderHash.out === traderCommitment;

    // 방향이 유효한지 검증 (0 또는 1)
    side * (1 - side) === 0;
}

component main {public [orderCommitment, nullifier, traderCommitment]} = DarkPoolOrder();
```

| **체결 품질** | 중간시장 가격이 공정성 보장 |
| **MEV 보호** | 주문이 검색자에게 보이지 않음 |
| **가격 발견** | 교차 메커니즘을 통해 보존됨 |
| **기관 접근** | 대규모 주문 체결 가능 |

## 보안 고려사항

| 위험 | 완화 |
|------|------------|
| **MPC 노드 공모** | 임계값 보안; 다양한 노드 운영자 |
| **주문 재전송** | Nullifier 추적; 타임스탬프 |
| **타이밍 공격** | 배치 매칭 라운드; 무작위 타이밍 |
| **서비스 거부** | 속도 제한; 보증금 요구사항 |
| **정산 실패** | 원자적 정산; 시간초과 환불 |
| **운영자 선행매매** | 임계값 복호화; 단일 운영자는 주문을 볼 수 없음 |

## 구현 과제

1. **MPC 성능**
   - 보안 연산은 평문보다 느림
   - 대규모 주문장은 효율적인 프로토콜 필요
   - 최적화된 MPC 프레임워크 고려 (MP-SPDZ, SCALE-MAMBA)

2. **노드 조정**
   - 분산 노드는 매칭 라운드에 합의해야 함
   - 네트워크 분할이 매칭을 지연시킬 수 있음
   - 비잔틴 내결함성 필요

3. **공정성 검증**
   - 사용자는 매칭이 공정했다고 신뢰해야 함
   - 올바른 매칭의 ZK 증명 고려
   - 주문을 공개하지 않는 감사 메커니즘

4. **유동성 단편화**
   - 다크풀이 공개 시장과 분리됨
   - 효과적인 매칭을 위한 임계 규모 필요
   - 하이브리드 공개/다크 체결 고려

5. **규제 준수**
   - 다크풀은 규제 감독 대상
   - 규제기관을 위한 선택적 공개 필요
   - 프라이버시를 깨지 않는 감사 추적

## 파생상품

1. **규모 기반 매칭** - 다크풀 접근을 위한 최소 주문 크기. 작은 탐지 주문으로부터 정보 유출 방지. 거래 규모에 따른 계층별 접근.

2. **시간 우선순위 매칭** - 교차 가격에서 제출 시간 순서대로 주문 매칭. 모든 참가자의 공정한 대우. 시간 기반 게이밍 방지.

3. **가격 개선** - 매칭된 주문이 지정가가 아닌 중간시장에서 체결. 양측 모두 스프레드 절감 혜택. 다크풀 사용 인센티브 제공.

4. **블록 거래** - 초대형 주문을 위한 예정된 매칭 세션. 특정 시간에 유동성 집계. 메가 주문의 시장 충격 감소.

5. **빙산 주문** - 작은 부분만 표시; 전체 크기 숨김. 전체를 공개하지 않고 분할 체결. 전통적인 빙산 기능을 비공개로 모방.

## 사용 사례

1. **기관 포트폴리오 리밸런싱**
   - 펀드가 $1천만 ETH 매도 필요
   - 공개 시장 체결은 가격을 2-3% 움직임
   - 다크풀이 ETH를 찾는 매수자와 매칭
   - 양측 모두 중간시장에서 체결; 시장 충격 없음

2. **재무 관리**
   - 프로토콜 재무가 보유 자산 다각화
   - 공개 매도는 신뢰 부족 신호
   - 다크풀이 비공개 다각화 가능
   - 시장이 매도 압력을 보지 못함

3. **인수합병 차익거래**
   - 차익거래자가 대상 회사 포지션 축적
   - 눈에 보이는 매수는 시장에 경고
   - 다크풀이 축적 전략 숨김
   - 신호 없이 포지션 구축

4. **인덱스 펀드 리밸런싱**
   - 인덱스 재구성은 대규모 거래 필요
   - 예측 가능한 거래가 거래자에게 악용됨
   - 다크풀 체결이 리밸런싱 숨김
   - 펀드 보유자에게 더 나은 체결

## 실제 제품 및 사용자 경험

### 1. "완전 비공개 거래소" - 거래 존재 자체를 숨기는 다크풀

**제품 설명**:
거래 금액, 참여자뿐 아니라 거래가 일어났다는 사실조차 외부에 알려지지 않는 완전 프라이버시 다크풀. 시장에서 어떤 신호도 발생하지 않습니다.

**일반 사용자 경험 (기관 관점)**:
- ABC 펀드는 $500만 ETH 매도 시 시장 영향 우려
- 일반 다크풀: 매칭 후 "큰 거래가 있었다" 신호 발생
- 완전 비공개 다크풀: 매칭 결과도 commitment로 숨김
- 외부에서는 거래 존재 자체를 알 수 없음
- 정산 후에도 "누군가 팔았다"는 사실조차 비공개

**관찰 가능한 이점**:
- "고래 움직임" 뉴스 자체가 발생하지 않음
- 거래 의도와 거래 사실 모두 비공개
- 시장 분석가도 대량 거래 추적 불가

### 2. "신원 격리 매칭" - 상대방도 모르는 거래

**제품 설명**:
거래가 체결된 후에도 누가 매수하고 누가 매도했는지 양쪽 모두 알 수 없는 완전 익명 매칭 서비스.

**일반 사용자 경험**:
- 김사장(50세)은 $100만 매도, 이대표(45세)는 매수 희망
- MPC 매칭: 주문이 매칭되지만 상대방 정보는 비공개
- 김사장은 "누가 내 물량을 샀는지" 모름
- 이대표는 "이 물량의 이전 소유자가 누구인지" 모름
- 거래 관계가 형성되지 않아 향후 추적도 불가

**관찰 가능한 이점**:
- 거래 상대방 프라이버시 완벽 보호
- "누가 누구에게 팔았다" 정보 원천 차단
- 거래 후 관계 추적 방지

### 3. "패턴 방지 실행" - 거래 행동 분석 차단

**제품 설명**:
대량 거래를 실행할 때 시간, 금액, 빈도 패턴이 외부에 노출되지 않아 행동 분석을 차단하는 서비스.

**일반 사용자 경험**:
- 이재무팀장은 매월 회사 자금 $50만씩 투자
- 일반 실행: "매월 $50만씩 사는 주소" 패턴 노출
- 패턴 방지: 금액, 타이밍이 무작위화되어 매칭
- 외부에서는 "정기 투자자"인지 알 수 없음
- 회사의 투자 전략과 자금 규모 추론 불가

**관찰 가능한 이점**:
- 투자 패턴으로 의도 추론 방지
- 정기 투자자 타겟팅 공격 차단
- 기업 재무 전략 비공개 유지
