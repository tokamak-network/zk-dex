# J8. 임계 서명

개인키를 재구성하지 않고 M-of-N 다자간 서명을 가능하게 하는 분산 키 관리로, 안전한 프로토콜 운영에 필수적.

**요구사항**: 분산 키 생성 | 임계 서명 프로토콜 | 키 갱신 메커니즘 | ZK 증명과의 통합

---

## 배경

단일 키 제어는 중대한 취약점을 만듭니다:

- **단일 실패 지점**: 키 유출은 완전한 손실을 의미
- **내부자 위험**: 키 보유자가 절대적인 제어권 가짐
- **가용성**: 키 보유자 부재 시 운영 차단
- **책임성**: 누가 승인했는지 추적 어려움

임계 서명은 다음을 통해 이를 해결합니다:
- 여러 당사자 간 키 분할
- M-of-N 당사자의 서명 요구
- 전체 키를 재구성하지 않음
- 안전한 분산 운영 가능

ZK-DEX에서 임계 서명은 안전한 프로토콜 관리, 브릿지 운영, 비상 제어를 가능하게 합니다.

## 기술 사양

### 아키텍처 개요

```
서명 요청                    임계 서명                          최종 서명
+-------------+               +------------------------+         +-------------+
|             |               |                        |         |             |
| 메시지 M    |               |  당사자 1 (공유 s1)     |         |  유효한     |
|             |-------------->|  당사자 2 (공유 s2)     |-------->|  서명       |
| 요구사항    |               |  당사자 3 (공유 s3)     |         |  (M에 대해) |
| 2-of-3      |               |  ...                   |         |             |
+-------------+               |  당사자 N (공유 sN)     |         +-------------+
                              |                        |
                              |  각 당사자:            |
                              |  1. 부분 계산          |
                              |  2. 부분 공유          |
                              |  3. M개 부분 결합      |
                              |                        |
                              |  키는 조립되지 않음    |
                              +------------------------+
```

### 컴포넌트 목록

| 컴포넌트 | 설명 |
|-----------|-------------|
| **DKG 프로토콜** | 초기 설정을 위한 분산 키 생성 |
| **서명 조정자** | 임계 서명 세션 조율 |
| **부분 서명 생성기** | 당사자의 서명 공유 계산 |
| **서명 결합기** | 부분 서명 집계 |
| **키 갱신** | 공개키 변경 없이 공유 업데이트 |
| **ZK 통합** | 임계 서명 유효성 증명 |

### 데이터 흐름

1. **키 생성 (DKG)**
   - N명의 당사자가 분산 키 생성에 참여
   - 각 당사자가 개인 공유 수신
   - 공개키 발표; 누구도 전체 개인키를 모름

2. **서명 프로토콜**
   - 서명할 메시지가 당사자들에게 배포
   - M명의 당사자가 부분 서명 계산
   - 부분 서명을 유효한 서명으로 결합

3. **키 갱신**
   - 주기적으로 공유 업데이트
   - 오래된 공유는 무효화
   - 공개키는 변경되지 않음

### 임계 서명 회로

```circom
pragma circom 2.1.0;

include "../utils/poseidon/poseidon.circom";
include "../utils/eddsa/eddsa_verify.circom";

template ThresholdSignatureProof(numParties, threshold) {
    // 공개 입력
    signal input message;             // 서명된 메시지
    signal input publicKey[2];        // 결합된 공개키
    signal input signature[2];        // 최종 임계 서명
    signal input participantMask;     // 참여 당사자의 비트맵

    // 비공개 입력
    signal input partialSignatures[numParties][2];  // 각 당사자의 부분 서명
    signal input participantShares[numParties];     // 공개키 공유
    signal input participantIndices[numParties];    // 라그랑주 인덱스

    // 참여자 수 계산
    signal participantCount;
    signal countBits[numParties];
    signal runningCount[numParties + 1];
    runningCount[0] <== 0;

    for (var i = 0; i < numParties; i++) {
        countBits[i] <== (participantMask >> i) & 1;
        runningCount[i + 1] <== runningCount[i] + countBits[i];
    }
    participantCount <== runningCount[numParties];

    // 임계값 충족 검증
    component thresholdCheck = GreaterEqThan(8);
    thresholdCheck.in[0] <== participantCount;
    thresholdCheck.in[1] <== threshold;
    thresholdCheck.out === 1;

    // 서명이 올바르게 결합되는지 검증
    // (단순화 - 실제 TSS는 라그랑주 보간 사용)
    component sigVerify = EdDSAVerify();
    sigVerify.message <== message;
    sigVerify.pubKey[0] <== publicKey[0];
    sigVerify.pubKey[1] <== publicKey[1];
    sigVerify.signature[0] <== signature[0];
    sigVerify.signature[1] <== signature[1];
    sigVerify.valid === 1;
}

component main {public [message, publicKey, signature, participantMask]} = ThresholdSignatureProof(5, 3);
```

### TSS 스킴

| 스킴 | 커브 | 라운드 | 특징 |
|--------|-------|--------|----------|
| **FROST** | Ed25519/secp256k1 | 2 | 유연성, 효율성 |
| **GG20** | secp256k1 | 4-5 | 견고함, 널리 구현됨 |
| **CGGMP** | secp256k1 | 4 | 식별 가능한 중단 |
| **Lindell17** | secp256k1 | 2 | 간단한 2-of-2 |

## 구현 과제

1. **조정 오버헤드**
   - 서명에 M명의 당사자 조정 필요
   - 네트워크 지연이 서명 시간에 추가
   - 비동기 프로토콜이 도움됨

2. **당사자 가용성**
   - M명의 당사자가 동시에 온라인 필요
   - 지리적 분산으로 타이밍 복잡화
   - 가용성 요구사항 신중히 고려

3. **키 생성 보안**
   - DKG가 가장 민감한 작업
   - 모든 당사자가 정직하게 참여해야 함
   - 여러 DKG 의식 고려

4. **갱신 물류**
   - 보안을 위해 정기적인 갱신 필요
   - 당사자들에게 조정 부담
   - 가능한 경우 자동화

5. **임계값 선택**
   - 높은 임계값 = 더 많은 보안, 적은 가용성
   - 낮은 임계값 = 더 많은 가용성, 적은 보안
   - 상황별 최적화

## 파생 기술

1. **TSS 키 생성** - 분산 키 생성 프로토콜. 신뢰할 수 있는 딜러 없음. 각 당사자가 무작위성 기여.

2. **서명 의식** - 조정된 서명 세션. 메시지 승인을 위한 정의된 프로토콜. 참여 감사 추적.

3. **키 갱신** - 공유 교체를 통한 사전적 보안. 갱신 후 오래된 공유 무효. 유출 창 제한.

4. **사전적 보안** - 임계값 변경 없는 정기 갱신. 이동 적대자 우려 제거. 장기 보안에 필수적.

5. **크로스체인 TSS** - 여러 체인을 위해 동일한 TSS 그룹 서명. 통합 키 관리. 효율적인 멀티체인 운영.

## 사용 사례

1. **프로토콜 재무**
   - TSS 지갑에 프로토콜 자금 보관
   - 지출에 3-of-5 멀티시그
   - 단일 관리자가 자금 탈취 불가
   - 투명한 거버넌스 통합

2. **브릿지 서명**
   - 크로스체인 브릿지에 서명 필요
   - TSS 위원회가 이전 승인
   - 탈중앙화 브릿지 보안
   - 신뢰할 수 있는 관리인 불필요

3. **비상 운영**
   - 프로토콜 일시정지에 TSS 서명 필요
   - 일방적 비상 조치 방지
   - M-of-N 합의로 신속한 대응
   - 책임 있는 비상 거버넌스

4. **오라클 서명**
   - TSS 위원회가 가격 피드에 서명
   - 단일 오라클이 조작 불가
   - 오라클 가용성에 내결함성
   - 검증 가능한 데이터 진위성

## 실제 제품 및 사용자 경험

### 1. "익명 서명자 금고" - 누가 승인했는지 숨김

**제품 설명**:
임계 서명으로 자산을 관리하면서 "누가 서명했는지"가 공개되지 않아 서명자에 대한 압력이나 타겟팅을 방지하는 프라이버시 금고.

**일반 사용자 경험**:
- 가족 자산 3-of-5 분산 금고 사용
- 일반 TSS: "아버지, 어머니, 변호사가 서명" 공개
- 익명 서명: "3명이 서명함"만 공개, 누구인지는 비밀
- 외부인이 "누가 자산 이동에 동의했는지" 알 수 없음
- 특정 서명자 협박/타겟팅 방지

**관찰 가능한 이점**:
- 서명자 개인에 대한 압력 방지
- 가족/조직 내 역학관계 비공개
- 서명 참여 사실 자체를 숨김

### 2. "비공개 노드 브릿지" - 어떤 노드가 승인했는지 숨김

**제품 설명**:
분산 브릿지에서 어떤 노드들이 서명에 참여했는지 공개되지 않아 "이 노드를 공격하면 브릿지 마비" 분석을 차단하는 프라이버시 브릿지.

**일반 사용자 경험**:
- 크로스체인 브릿지 사용 (10-of-15 노드 승인)
- 일반 브릿지: "노드 1, 3, 5, 7, 9...가 서명" 공개
- 비공개 브릿지: "10개 이상 서명 완료"만 공개
- 공격자가 "어느 노드가 활성인지" 파악 불가
- 특정 노드 타겟 공격으로 브릿지 마비 시도 차단

**관찰 가능한 이점**:
- 활성 노드 식별 방지
- 노드 타겟팅 공격 차단
- 서명 참여 패턴 분석 불가

### 3. "프라이빗 거버넌스 서명" - DAO 키홀더 익명성

**제품 설명**:
DAO 트레저리 관리에서 어떤 키홀더들이 서명했는지 공개되지 않아 내부 정치와 외부 압력으로부터 키홀더를 보호하는 프라이버시 거버넌스.

**일반 사용자 경험 (DAO 관점)**:
- 논쟁적인 지출 제안에 5-of-9 서명 필요
- 일반 TSS: "개발자 A, B, 커뮤니티 C, D, E가 서명" 공개
- 프라이빗 TSS: "5명 이상 서명 완료"만 공개
- 반대파가 "누가 이 지출에 동의했나" 추적 불가
- 키홀더들이 정치적 부담 없이 소신 서명 가능

**관찰 가능한 이점**:
- 키홀더의 정치적 압력으로부터 보호
- 서명 결정에 대한 보복 방지
- 독립적인 판단 가능한 환경
