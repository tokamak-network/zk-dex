# J7. VDF 통합

공정한 프로토콜 운영에 필수적인 예측 불가능하지만 검증 가능한 무작위성을 제공하는 검증 가능한 지연 함수.

**요구사항**: VDF 계산 인프라 | 검증 회로 | 무작위성 비콘 | 프로토콜 운영과의 통합

---

## 배경

공정한 프로토콜은 예측 불가능한 무작위성이 필요하지만, 블록체인 무작위성은 문제가 있습니다:

- **채굴자/검증자 조작**: 블록 제안자가 블록 해시에 영향을 줄 수 있음
- **프론트러닝**: 예측 가능한 무작위성으로 MEV 추출 가능
- **편향 공격**: 참여자가 선택적으로 공개하여 결과 편향 가능
- **타이밍 게임**: 커밋-공개 스킴에서 마지막 공개자 이점

VDF는 다음을 통해 이를 해결합니다:
- 병렬화할 수 없는 순차적 계산 요구
- 효율적으로 검증 가능한 출력 생성
- 계산 완료까지 누구도 출력을 예측할 수 없음
- 무신뢰 무작위성 비콘 가능

ZK-DEX에서 VDF는 공정한 주문 매칭, 편향 없는 청산, MEV 저항 운영을 가능하게 합니다.

## 기술 사양

### 아키텍처 개요

```

+-------------+               +------------------------+         +-------------+
|             |               |                        |         |             |
| 블록 해시   |               |  순차적                 |  증명   |  검증 가능한|
| + 논스      |-------------->|  계산                  |-------->|  무작위     |
|             |               |  (T 시간 단계)         |         |  값         |
+-------------+               |                        |         +-------------+
                              |  +----------------+    |              |
                              |  | 병렬화         |    |              v
                              |  | 불가능         |    |         +-------------+
                              |  +----------------+    |         | 프로토콜    |
                              |         |              |         | 무작위성    |
                              |         v              |         | 사용        |
                              |  +----------------+    |         +-------------+
                              |  | 효율적         |    |
                              |  | 검증           |    |
                              |  +----------------+    |
                              +------------------------+
```

### 컴포넌트 목록

| 컴포넌트 | 설명 |
|-----------|-------------|
| **VDF 계산기** | 순차적 VDF 계산 수행 |
| **증명 생성기** | 올바른 계산의 증명 생성 |
| **검증 회로** | 온체인에서 VDF 출력 검증 |
| **무작위성 비콘** | 프로토콜에 VDF 출력 배포 |
| **시드 관리자** | VDF 시드를 위한 입력 결합 |
| **타이밍 오라클** | 충분한 지연 경과 보장 |

### 데이터 흐름

1. **시드 생성**
   - 공개 입력 결합 (블록 해시, 커밋먼트)
   - 예측 불가능한 시드 생성
   - VDF 계산 시작

2. **VDF 계산**
   - T 단계 동안 순차적 계산 실행
   - 크게 가속화될 수 없음
   - 출력과 증명 생성

3. **검증 및 사용**
   - 검증기에 출력과 증명 제출
   - 효율적인 검증으로 정확성 확인
   - 프로토콜이 무작위 값 사용

### VDF 검증 회로

```circom
pragma circom 2.1.0;

include "../utils/poseidon/poseidon.circom";

// 단순화된 VDF 검증
// 실제 구현은 특화된 구성 사용 (Wesolowski, Pietrzak)

template VDFVerifier(numSteps) {
    // 공개 입력
    signal input seed;           // VDF 입력
    signal input output;         // 주장된 VDF 출력
    signal input proofCommitment; // 검증 증명의 커밋먼트

    // 비공개 입력
    signal input intermediateStates[numSteps];  // 계산 추적
    signal input proofElements[100];            // Wesolowski/Pietrzak 증명

    // 계산 체인 검증
    // 실제 VDF에서는 RSA 그룹의 반복 제곱
    // 또는 유사한 대수 구조 사용

    component stepHash[numSteps];
    signal chainValue[numSteps + 1];
    chainValue[0] <== seed;

    for (var i = 0; i < numSteps; i++) {
        stepHash[i] = Poseidon(2);
        stepHash[i].inputs[0] <== chainValue[i];
        stepHash[i].inputs[1] <== i;  // 단계 카운터
        chainValue[i + 1] <== stepHash[i].out;

        // 중간 상태 일치 검증
        chainValue[i + 1] === intermediateStates[i];
    }

    // 최종 출력 검증
    chainValue[numSteps] === output;

    // 증명 커밋먼트 검증
    component proofHash = Poseidon(100);
    for (var i = 0; i < 100; i++) {
        proofHash.inputs[i] <== proofElements[i];
    }
    proofHash.out === proofCommitment;
}

component main {public [seed, output, proofCommitment]} = VDFVerifier(1000);
```

### VDF 구성

| 구성 | 보안 근거 | 검증 | 참고 |
|--------------|---------------|--------------|-------|
| **Wesolowski** | RSA 가정 | O(1) | 단일 지수화 |
| **Pietrzak** | RSA 가정 | O(log T) | 대화형에서 비대화형으로 |
| **MinRoot** | 해시 함수 | O(T) | 단순하지만 느린 검증 |
| **Sloth++** | 모듈러 제곱근 | O(1) | 신뢰할 수 있는 설정 필요 |

## 효과

| 측면 | 영향 |
|--------|--------|
| **예측 불가능성** | 계산 완료까지 출력 알 수 없음 |
| **검증 가능성** | 누구나 출력이 올바른지 검증 가능 |
| **공정성** | 어떤 참여자도 결과를 편향시킬 수 없음 |
| **MEV 저항** | 예측 가능한 무작위성 기반 프론트러닝 방지 |
| **무신뢰성** | 무작위성에 신뢰할 수 있는 당사자 불필요 |
| **적시성** | 알려진 지연으로 프로토콜 타이밍 가능 |

## 구현 과제

1. **하드웨어 경쟁**
   - ASIC이 VDF 계산 가속화 가능
   - 하드웨어 발전 모니터링 필요
   - 시간 파라미터 조정 필요 가능

2. **계산 비용**
   - VDF 계산은 의도적으로 비쌈
   - 전용 인프라 필요
   - 탈중앙화 VDF 네트워크 고려

3. **검증 효율성**
   - 온체인 검증이 효율적이어야 함
   - Wesolowski/Pietrzak은 상수/로그 검증 가능
   - ZK 검증을 위한 회로 복잡성

4. **시드 신선도**
   - 계산 시작 시 시드가 예측 불가능해야 함
   - 커밋-공개 또는 미래 블록 해시
   - 신선도와 가용성 간 트레이드오프

5. **통합 타이밍**
   - 프로토콜이 VDF 완료를 기다려야 함
   - 사용자 경험에 지연 영향
   - 비동기 패턴 고려

## 파생 기술

1. **무작위 비콘** - VDF 생성 무작위성의 지속적인 스트림. 에포크마다 새 값. 공개 무작위성 인프라.

2. **복권 시스템** - VDF 무작위성으로 공정한 당첨자 선정. 누구도 당첨자 예측 또는 영향 불가. 무신뢰 복권 프로토콜.

3. **리더 선정** - 블록 제안자 또는 시퀀서를 공정하게 선택. 선정 조작 방지. PoS 시스템에 필수적.

4. **무작위성 커밋먼트** - 알려지기 전에 미래 무작위성에 커밋. 증명 가능하게 공정한 결과 가능. 봉인 입찰 애플리케이션.

5. **지연 타워** - 시간 증명을 위한 VDF 체인. 작업 증명의 대안. 시간 기반 합의 메커니즘.

## 사용 사례

1. **공정한 주문 매칭**
   - 배치로 주문 제출
   - VDF 무작위성이 매칭 순서 결정
   - 시퀀서의 프론트러닝 방지
   - 모든 참여자에게 공정한 실행

2. **편향 없는 청산**
   - 여러 청산자가 적격
   - VDF 무작위성이 실행자 선정
   - MEV 기반 청산 게임 방지
   - 청산 보상의 공정한 분배

3. **NFT 민팅**
   - 희귀 특성이 무작위로 할당
   - VDF가 공정성 보장
   - 내부자 이점 없음
   - 증명 가능하게 공정한 분배

4. **거버넌스 타이브레이커**
   - 동점 투표를 공정하게 해결
   - VDF 무작위성이 결과 결정
   - 조작 불가능
   - 모든 당사자가 수용 가능

## 실제 제품 및 사용자 경험

### 1. "익명 공정 추첨" - 참여자 신원 숨김 + 공정성

**제품 설명**:
VDF로 공정한 추첨을 하면서도 누가 참여했는지, 누가 당첨되었는지 신원이 공개되지 않는 프라이버시 추첨.

**일반 사용자 경험**:
- 인기 NFT 화이트리스트 추첨 참여
- 일반 추첨: "이 주소들이 참여, 이 주소가 당첨" 공개
- 익명 추첨: 참여 commitment만 제출, 신원 숨김
- VDF 결과로 당첨 여부 결정되지만 "누가 당첨"은 비공개
- 당첨자만 자신이 당첨임을 ZK로 증명하여 수령
- 참여 명단과 당첨자 명단 모두 비공개

**관찰 가능한 이점**:
- 추첨 참여 사실 자체가 비공개
- 당첨자 타겟팅 방지
- 공정성과 프라이버시 동시 확보

### 2. "숨겨진 순서 매칭" - 최종 순서도 비공개

**제품 설명**:
VDF로 주문 순서를 결정하되, 최종 순서가 공개되지 않아 "누가 먼저 체결됐는지" 분석이 불가능한 프라이버시 매칭.

**일반 사용자 경험**:
- DEX에서 대량 스왑 실행
- 일반 VDF 매칭: 공정하지만 "A가 1등, B가 2등" 순서 공개
- 숨겨진 매칭: VDF로 순서 결정 후 순서 자체를 숨김
- "내 주문이 몇 번째인지"는 나만 알 수 있음
- 순서 기반 분석으로 전략 추론 방지

**관찰 가능한 이점**:
- 체결 순서 정보로 전략 분석 차단
- "빠른 주문 = 급한 거래" 추론 방지
- 매칭 결과의 완전한 프라이버시

### 3. "비공개 선정" - 누가 선정됐는지 숨김

**제품 설명**:
VDF로 공정하게 리더/참여자를 선정하되, 선정 결과가 필요한 시점까지 공개되지 않아 사전 타겟팅이 불가능한 시스템.

**일반 사용자 경험 (밸리데이터 관점)**:
- PoS 네트워크 밸리데이터 참여 중
- 일반 VDF 선정: "다음 리더는 A" 공개 → A 타겟 공격 가능
- 비공개 선정: 선정 결과가 암호화되어 본인만 앎
- 선정된 밸리데이터만 "내가 리더"임을 알고 블록 생성
- 공격자는 누가 리더인지 블록 발표 전까지 모름

**관찰 가능한 이점**:
- 리더 사전 타겟팅 공격 방지
- 선정 결과의 프라이버시 보호
- 공정성과 보안의 동시 강화
