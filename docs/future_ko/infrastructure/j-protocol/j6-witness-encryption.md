# J6. 위트니스 암호화

조건이 충족됨을 증명해야만 복호화가 가능하도록 임의의 조건에 암호화할 수 있는 암호학적 프리미티브.

**요구사항**: 위트니스 암호화 스킴 | 조건 회로 | 복호화 프로토콜 | ZK 시스템과의 통합

---

## 배경

전통적인 암호화는 조건부 접근에 한계가 있습니다:

- **키 관리**: 사전 공유 키 또는 PKI 필요
- **신뢰 요구사항**: 조건을 위해 신뢰할 수 있는 당사자 필요
- **타이밍 제약**: 미래 조건에 암호화하기 어려움
- **조합성**: 여러 조건 결합이 어려움

위트니스 암호화는 다음을 통해 이를 해결합니다:
- 조건에 직접 암호화 (예: "f(x) = y를 만족하는 x를 알면 복호화 가능")
- 조건 강제에 신뢰할 수 있는 설정 불필요
- ZK 증명 시스템과의 자연스러운 통합
- 새로운 타임락 및 조건부 접근 패턴 가능

ZK-DEX에서 이는 고급 조건부 거래 및 타임락 메커니즘을 가능하게 합니다.

## 기술 사양

### 아키텍처 개요

```
암호화자                      위트니스 암호화                     복호화자
+-------------+               +------------------------+         +-------------+
|             |  조건 C에     |                        |         |             |
| 메시지 M    |  암호화       |  암호문 CT              |  위트니스| 복원된      |
|             |-------------->|  (C에 바인딩)           |<--------|  M          |
| 조건:       |               |                        |  증명   |             |
| "x: f(x)=y" |               +------------------------+         +-------------+
+-------------+                        |
                                       | 유효한 위트니스를
                                       | 가진 사람은 복호화 가능
                                       v
                              +------------------------+
                              |  복호화 요구사항:      |
                              |  - 유효한 위트니스 w   |
                              |  - f(w) = y 증명      |
                              +------------------------+
```

| **조합 계층** | 여러 조건 결합 |

### 데이터 흐름

1. **암호화**
   - 조건을 NP 명제로 정의
   - 조건에 메시지 암호화
   - 암호문은 위트니스로만 복호화 가능

2. **위트니스 획득**
   - 복호화자가 위트니스 획득 (예: 계산, 시간 경과)
   - 위트니스가 조건을 만족해야 함
   - ZK 증명 생성 포함 가능

3. **복호화**
   - 복호화 알고리즘에 위트니스 제출
   - 알고리즘이 위트니스가 조건을 만족하는지 검증
   - 위트니스가 유효하면 메시지 복원

### 위트니스 암호화 통합

```circom
pragma circom 2.1.0;

include "../utils/poseidon/poseidon.circom";

template WitnessDecryption() {
    // 공개 입력
    signal input ciphertextCommitment;  // 암호화된 데이터의 커밋먼트
    signal input conditionHash;          // 조건의 해시
    signal input decryptedCommitment;    // 복호화 결과의 커밋먼트

    // 비공개 입력
    signal input witness[10];            // 조건을 만족하는 위트니스
    signal input encryptedData[10];      // 암호화된 메시지
    signal input decryptionKey;          // 위트니스에서 파생된 키
    signal input decryptedData[10];      // 결과 평문
    signal input salt;

    // 위트니스가 조건을 만족하는지 검증
    // (조건별 검증이 여기에 들어감)
    component conditionCheck = ConditionVerifier();
    for (var i = 0; i < 10; i++) {
        conditionCheck.witness[i] <== witness[i];
    }
    conditionCheck.conditionHash <== conditionHash;
    conditionCheck.satisfied === 1;

    // 위트니스에서 복호화 키 파생
    component keyDerivation = Poseidon(10);
    for (var i = 0; i < 10; i++) {
        keyDerivation.inputs[i] <== witness[i];
    }
    keyDerivation.out === decryptionKey;

    // 복호화가 올바른지 검증
    component decryptVerify = SymmetricDecrypt();
    decryptVerify.key <== decryptionKey;
    for (var i = 0; i < 10; i++) {
        decryptVerify.ciphertext[i] <== encryptedData[i];
        decryptVerify.plaintext[i] <== decryptedData[i];
    }

    // 복호화된 데이터에 커밋
    component decryptCommit = Poseidon(11);
    for (var i = 0; i < 10; i++) {
        decryptCommit.inputs[i] <== decryptedData[i];
    }
    decryptCommit.inputs[10] <== salt;
    decryptCommit.out === decryptedCommitment;
}

component main {public [ciphertextCommitment, conditionHash, decryptedCommitment]} = WitnessDecryption();
```

## 구현 과제

1. **효율적인 구성**
   - 순수 위트니스 암호화는 이론적/비효율적
   - 실용적 구성은 가정 사용 (예: 난독화, 다중선형 맵)
   - 실용적 대안으로 함수형 암호화 고려

2. **조건 표현력**
   - 모든 조건을 효율적으로 표현할 수 있는 것은 아님
   - 회로 크기가 실용적 조건을 제한
   - 표현력과 효율성 간 트레이드오프

3. **위트니스 생성**
   - 복호화자가 위트니스를 획득할 수 있어야 함
   - 일부 조건은 위트니스 획득이 어려움
   - 설계 시 위트니스 가용성 고려

4. **통합 복잡성**
   - 기존 ZK 인프라와 통합되어야 함
   - 위트니스 암호화가 오버헤드 추가
   - 기능과 복잡성 간 균형

5. **표준화**
   - 널리 채택된 표준 없음
   - 상호운용성 문제
   - 업계 협력 필요

## 파생 기술

1. **타임락 암호화** - 미래 블록체인 상태로 암호화 (예: 블록 해시). 시간이 지나야만 복호화 가능. 봉인 입찰 경매에 유용.

2. **조건 기반 복호화** - 임의의 조건 충족 시 복호화. 가격이 임계값 도달, 이벤트 발생 등. 프로그래밍 가능한 조건부 접근.

3. **임계값 복호화** - 복호화에 M-of-N 위트니스 필요. 분산 신뢰 모델. 위트니스 암호화와 결합.

4. **함수형 암호화** - 평문의 특정 함수만 복호화. 완전한 위트니스 암호화보다 약함. 더 효율적인 구성 가능.

5. **속성 기반 암호화** - 속성 정책으로 암호화. 복호화에 일치하는 속성 필요. 조건부 암호화의 실용적 형태.

## 사용 사례

1. **봉인 입찰 경매**
   - 입찰자가 미래 블록 해시로 입찰 암호화
   - 공개 시간 전에 누구도 입찰 볼 수 없음
   - 블록이 채굴된 후에만 복호화 가능
   - 무신뢰 봉인 입찰 메커니즘

2. **조건부 주문**
   - 가격 조건에 주문 암호화
   - "ETH > $5000일 때 복호화 및 실행"
   - 조건이 충족될 때까지 주문 숨김
   - MEV 저항 조건부 거래

3. **타임락 비밀**
   - 미래 시간에 개인키 암호화
   - 무신뢰 키 에스크로 가능
   - 데드맨 스위치 애플리케이션
   - 예약된 정보 공개

4. **프라이빗 스마트 컨트랙트**
   - 접근 조건에 컨트랙트 상태 암호화
   - 권한 있는 당사자만 읽기 가능
   - 조건이 암호학적으로 강제됨
   - 신뢰할 수 있는 실행 환경 불필요

## 실제 제품 및 사용자 경험

### 1. "프라이빗 유산 전달" - 수취인도 조건 전까지 모름

**제품 설명**:
디지털 유산을 특정 조건 충족 시에만 접근 가능하게 암호화하되, 조건이 무엇인지도 수취인에게 숨길 수 있는 프라이버시 유산 계획.

**일반 사용자 경험**:
- 김유산(65세)은 특정 조건 충족 시 자녀에게 유산 전달 희망
- 일반 타임락: "2030년에 열림" 조건이 공개됨
- 프라이빗 유산: 조건 자체도 암호화됨
- 자녀는 "언제, 어떤 조건에 열리는지"도 모름
- 조건 충족 시 자동으로 복호화되어 알림
- 유산 계획의 완전한 비밀 유지

**관찰 가능한 이점**:
- 유산 존재 여부도 비밀 유지 가능
- 조건 공개로 인한 행동 변화 방지
- 완전히 프라이빗한 유산 계획

### 2. "숨겨진 조건부 주문" - 조건 자체도 비밀

**제품 설명**:
조건부 주문에서 "어떤 조건에 실행되는지"까지 숨겨 전략 의도가 완전히 비공개인 프라이버시 주문.

**일반 사용자 경험**:
- 트레이더 이조건씨는 특정 조건에 매도 희망
- 일반 조건부: "ETH $5,000이면 매도" 조건 공개 → 전략 노출
- 숨겨진 조건부: 조건 자체가 암호화됨
- 시장 참여자들은 "어떤 조건의 주문이 대기 중인지" 모름
- 조건 충족 시에만 주문 존재가 드러남
- 전략 의도 완전 숨김

**관찰 가능한 이점**:
- 거래 조건으로 전략 추론 방지
- "이 가격대에 물량 대기" 정보 숨김
- 조건부 주문의 완전한 프라이버시

### 3. "영구 비밀 입찰" - 낙찰 외 입찰가 영원히 비공개

**제품 설명**:
경매에서 낙찰된 입찰가만 공개되고, 나머지 입찰가는 영원히 복호화되지 않아 "얼마까지 쓸 용의가 있었는지" 비밀이 유지되는 경매.

**일반 사용자 경험**:
- NFT 경매에서 박입찰씨가 $10,000에 낙찰
- 일반 비밀 입찰: 종료 후 모든 입찰가 공개 → "김씨는 $8K만 쓸 용의"
- 영구 비밀: 낙찰가($10K)만 공개, 다른 입찰은 영원히 암호화
- 탈락자들의 "지불 의향" 정보가 보호됨
- 향후 협상에서 약점으로 사용될 정보 차단

**관찰 가능한 이점**:
- 비낙찰 입찰자의 지불 의향 비공개
- 경매 데이터로 협상력 약화 방지
- 참여자 프라이버시 최대화
