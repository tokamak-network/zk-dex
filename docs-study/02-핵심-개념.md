# 핵심 개념

## 1. 노트 (Note)

**노트**는 ZK-DEX의 기본 가치 단위입니다. Bitcoin의 UTXO처럼 "소비되지 않은 잔액"을 표현합니다.

### 노트 = 7개 필드

```
Note = {
  owner0,      // 소유자 공개키 X 좌표 (pkX)
  owner1,      // 소유자 공개키 Y 좌표 (pkY)
  value,       // 금액 (wei 단위)
  tokenType,   // 0=ETH, 1=DAI
  vk0,         // Viewing Key X (= pkX)
  vk1,         // Viewing Key Y (= pkY)
  salt         // 랜덤값 (동일 노트 구분용)
}
```

**왜 salt가 필요한가?**
- salt 없이 같은 소유자가 같은 금액의 ETH를 입금하면 해시가 동일해짐
- 외부에서 "같은 사람이 같은 금액을 입금했다"는 것을 추론 가능
- salt로 모든 노트를 유일하게 만듦

---

## 2. 노트 해시 (Note Hash)

노트의 7개 필드를 Poseidon 해시로 압축한 값입니다.

```
noteHash = Poseidon(owner0, owner1, value, tokenType, vk0, vk1, salt)
```

**온체인에는 이 해시만 저장됨!**
- 원본 데이터 없이는 노트 내용을 알 수 없음
- 254비트 필드 원소 하나로 압축

---

## 3. 노트 상태 (Note State)

온체인 컨트랙트가 각 노트의 생명주기를 추적합니다.

```
Invalid(0) ──mint──▶ Valid(1) ──spend──▶ Spent(3)
                        │
                        └──makeOrder──▶ Trading(2)
```

| 상태 | 설명 |
|------|------|
| `Invalid` | 존재하지 않거나 소비된 노트 |
| `Valid` | 유효한 노트, 사용 가능 |
| `Trading` | 주문에 잠긴 노트 |
| `Spent` | 소비 완료, 재사용 불가 |

---

## 4. 계정 시스템 (두 개의 키)

ZK-DEX에서는 **두 가지 키 체계**가 독립적으로 존재합니다.

### Ethereum 계정 (MetaMask)
- secp256k1 키 쌍
- 트랜잭션 제출, 가스비 지불에 사용
- 노트 소유권과 **무관**

### ZK 계정 (BabyJubJub)
- BabyJubJub 타원곡선 키 쌍
- 노트 소유권 증명에 사용
- **이것만 알면 노트를 제어 가능**

```
┌──────────────────────────────────────────────┐
│  중요: ZK 비밀키(sk)만 있으면                    │
│  어떤 이더리움 계정에서든 노트를 제어 가능!        │
└──────────────────────────────────────────────┘
```

| 키 유형 | 역할 | 유출 시 |
|---------|------|---------|
| 이더리움 개인키 | 가스 지불 | ZK 노트 영향 없음 |
| ZK 비밀키 (sk) | 노트 소유 | **모든 노트 탈취 가능** |

---

## 5. 소유권 증명

노트 소유를 증명하는 방법:

```
1. 비밀키(sk)에서 공개키(pk) 계산
   pk = sk × G  (BabyJubJub 스칼라 곱셈)

2. 노트의 owner0, owner1과 비교
   owner0 == pk.x && owner1 == pk.y

3. 회로 내에서 검증 → sk가 외부에 노출되지 않음!
```

**온체인에서는 ZK 증명만 검증하면 됨**

## 6. 스마트 노트 (Smart Note)

소유자가 "공개키"가 아닌 **"다른 노트의 해시"**에서 파생된 특수 노트입니다.

### 일반 노트 vs 스마트 노트

| 속성 | 일반 노트 | 스마트 노트 |
|------|-----------|------------|
| owner0 | pkX | parentHash >> 128 |
| owner1 | pkY | parentHash & MASK |
| 용도 | 일반 전송 | 주문 체결 |

### 왜 필요한가?

주문 체결 시 "이 노트는 저 노트의 소유자에게 귀속된다"는 것을 **암호학적으로 강제**하기 위함입니다.

```
메이커 노트 → 스테이크 노트의 소유자 파생
             (owner0 = makerHash >> 128)
             (owner1 = makerHash & MASK)
```

스마트 노트는 `convertNote`로 일반 노트로 변환해야 자유롭게 사용 가능합니다.

## 7. Viewing Key (뷰잉 키)

현재 구현에서 뷰잉 키는 **공개키 자체**입니다.

```
vk0 = pkX
vk1 = pkY
```

### 주요 용도

1. **노트 탐색**: 온체인 암호화된 노트 중 내 것을 식별
2. **선택적 공개**: 제3자에게 노트 데이터 공유 (감사 등)
3. **스마트 노트 연결**: 부모-자식 노트 관계 강제

### 주의사항

**뷰잉 키만으로 온체인 노트를 복호화할 수 없음!**
- 현재 구현은 ECDH + AES-256-GCM 단일 계층
- 복호화에는 반드시 비밀키(sk)가 필요

---

## 8. 노트 암호화 (ECDH)

노트 데이터는 수신자만 복호화할 수 있도록 암호화되어 온체인에 저장됩니다.

### 암호화 과정

```
1. 임시 키 쌍 생성: (esk, epk)
2. 공유 비밀 계산: shared = esk × recipientPk
3. AES 키 파생: aesKey = SHA256(shared.x || shared.y)
4. 암호화: ciphertext = AES-256-GCM(aesKey, nonce, plaintext)
```

### 온체인 저장 형식

```
0x01 || epk_x(32B) || epk_y(32B) || nonce(12B) || ciphertext || authTag(16B)
```

### 복호화

수신자는 자신의 sk로 동일한 공유 비밀을 계산하여 복호화합니다.

```
shared = sk × epk  (송신자가 사용한 epk)
aesKey = SHA256(shared.x || shared.y)
plaintext = AES-256-GCM.decrypt(aesKey, nonce, ciphertext)
```

## 9. 암호학 기본 요소 정리

| 요소 | 용도 | 특징 |
|------|------|------|
| **Poseidon** | 노트 해시 | ZK 친화적, SHA256보다 ~100배 효율적 |
| **BabyJubJub** | 공개키/소유권 | 254비트 타원곡선 |
| **Groth16** | 증명 시스템 | 256바이트 증명, ~200K 가스 검증 |
| **BN128** | 페어링 곡선 | Ethereum precompile 지원 |
| **ECDH + AES-GCM** | 노트 암호화 | 수신자만 복호화 가능 |

## 10. FAQ

### Q: sk를 잃으면?
**A: 노트 영구 손실.** 온체인 암호화 데이터를 복호화할 수 없고, 소유권도 증명 불가.

### Q: 로컬 노트 데이터를 잃으면?
**A: sk가 있으면 복구 가능.** 온체인에 저장된 암호화 데이터를 sk로 복호화하면 됨.

### Q: 왜 두 개의 키 체계가 필요한가?
**A: 역할 분리.** 이더리움 키는 트랜잭션 제출용, ZK 키는 프라이버시 보호용.
