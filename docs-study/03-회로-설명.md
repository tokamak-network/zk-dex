# ZK 회로 설명

## 개요

ZK-DEX는 6개의 Circom 회로를 사용합니다. 모두 Groth16 증명 시스템(BN128 곡선)으로 컴파일됩니다.

| 회로 | 용도 | 제약 조건 수 |
|------|------|-------------|
| `mint_burn_note` | 입금/출금 | ~131K |
| `transfer_note` | 프라이빗 전송 | ~516K |
| `make_order` | 주문 생성 | ~131K |
| `take_order` | 주문 수락 | ~258K |
| `settle_order` | 주문 체결 | ~641K |
| `convert_note` | 스마트노트 변환 | ~385K |

---

## 1. mint_burn_note (노트 생성/소각)

ETH/DAI를 입금하여 노트를 생성하거나, 노트를 소각하여 출금합니다.

### 공개 입력 (4개)

| 인덱스 | 이름 | 설명 |
|--------|------|------|
| 0 | output | 항상 1 (유효성 마커) |
| 1 | noteHash | 노트의 Poseidon 해시 |
| 2 | value | 금액 (**공개**) |
| 3 | tokenType | 토큰 종류 |

### 비공개 입력

```
owner0, owner1, vk0, vk1, salt, sk
```

### 회로가 검증하는 것

1. **소유권**: sk → pk 계산 후 owner0/owner1과 일치 확인
2. **해시 일치**: Poseidon(7개 필드) == 공개 입력 noteHash
3. **값 일치**: 노트의 value, tokenType == 공개 입력

### 왜 value가 공개인가?

컨트랙트가 `msg.value`(실제 입금액)와 노트 금액의 일치를 검증해야 하기 때문입니다. 시스템 경계에서 불가피한 정보 공개입니다.

```solidity
// 온체인 컨트랙트
require(msg.value == input[2], "Value mismatch");
```

## 2. transfer_note (프라이빗 전송)

1~2개의 노트를 소비하고 2개의 새 노트(수신자 + 거스름돈)를 생성합니다.

### 공개 입력 (5개)

| 인덱스 | 이름 | 설명 |
|--------|------|------|
| 0 | output | 항상 1 |
| 1 | o0Hash | 입력 노트 0의 해시 |
| 2 | o1Hash | 입력 노트 1의 해시 (없으면 EMPTY_NOTE_HASH) |
| 3 | newHash | 수신자 노트의 해시 |
| 4 | changeHash | 거스름돈 노트의 해시 |

### 비공개 입력

- 입력 노트 2개의 전체 필드
- 출력 노트 2개의 전체 필드
- 비밀키 sk0, sk1

### 회로가 검증하는 것

1. **소유권**: 입력 노트 소유 증명
2. **해시 일치**: 4개 노트 모두 해시 검증
3. **가치 보존**: `input0.value + input1.value == new.value + change.value`
4. **토큰 일관성**: 모든 노트의 tokenType이 동일

### 핵심 특성

**value, owner가 공개 입력에 없음 → 완전한 프라이버시!**

외부에서 볼 수 있는 것: 해시 4개뿐
- 누가 누구에게 얼마를 보냈는지 알 수 없음
- 가치 보존은 회로 내부에서만 검증

---

## 3. make_order (주문 생성)

메이커가 자신의 노트로 거래 주문을 생성합니다.

### 공개 입력 (3개)

| 인덱스 | 이름 | 설명 |
|--------|------|------|
| 0 | output | 항상 1 |
| 1 | noteHash | 메이커 노트의 해시 |
| 2 | tokenType | 제공하는 토큰 종류 |

### 비공개 입력

```
owner0, owner1, value, vk0, vk1, salt, sk
```

### 회로가 검증하는 것

1. **소유권**: 메이커가 해당 노트를 소유
2. **해시 일치**: 노트 해시 검증

**value는 비공개** - 주문 금액을 숨긴 채 주문 가능

---

## 4. take_order (주문 수락)

테이커가 메이커 주문에 자산을 스테이크합니다.

### 공개 입력 (7개)

| 인덱스 | 이름 | 설명 |
|--------|------|------|
| 0 | output | 항상 1 |
| 1 | parentNoteHash | 테이커 원본 노트 해시 |
| 2 | parentNoteType | 원본 노트 토큰 종류 |
| 3 | stakeNoteHash | 스테이크 노트 해시 |
| 4 | stakeNoteOwner0 | = makerNoteHash >> 128 |
| 5 | stakeNoteOwner1 | = makerNoteHash & MASK |
| 6 | stakeNoteType | 스테이크 노트 토큰 종류 |

### 핵심 메커니즘: 스마트 노트 생성

```
테이커 노트 → 스테이크 노트 (스마트 노트)

스테이크 노트의 소유자:
  owner0 = makerNoteHash >> 128   (상위 128비트)
  owner1 = makerNoteHash & MASK   (하위 128비트)
```

**메이커 노트 해시에서 소유자가 파생** → 메이커만 해당 스테이크를 체결할 수 있음

### 회로가 검증하는 것

1. **소유권**: 테이커가 부모 노트 소유
2. **가치 보존**: `parentNote.value == stakeNote.value`
3. **스마트 노트 연결**: owner0/owner1이 makerHash에서 올바르게 파생

---

## 5. settle_order (주문 체결)

메이커와 테이커의 자산을 원자적으로 교환합니다. **가장 복잡한 회로**입니다.

### 공개 입력 (16개)

| 인덱스 | 이름 | 설명 |
|--------|------|------|
| 0 | output | 항상 1 |
| 1 | o0Hash | 메이커 노트 해시 |
| 2 | o0Type | 메이커 노트 토큰 |
| 3 | o1Hash | 스테이크 노트 해시 |
| 4 | o1Type | 스테이크 노트 토큰 |
| 5 | n0Hash | 보상 노트 해시 (테이커에게) |
| 6-7 | n0Owner0/1 | 보상 노트 소유자 (parentHash에서 파생) |
| 8 | n0Type | 보상 노트 토큰 |
| 9 | n1Hash | 지불 노트 해시 (메이커에게) |
| 10-11 | n1Owner0/1 | 지불 노트 소유자 (makerHash에서 파생) |
| 12 | n1Type | 지불 노트 토큰 |
| 13 | n2Hash | 잔돈 노트 해시 |
| 14 | n2Type | 잔돈 노트 토큰 |
| 15 | price | 교환 비율 |

### 가격 계산 (회로 내부)

ZK 회로에서는 나눗셈을 직접 수행할 수 없어 **비결정론적 검증**을 사용합니다.

```
makerValue × price = q0 × 10^18 + r0    (나머지 r0 < 10^18)
takerValue = q1 × price + r1            (나머지 r1 < price)
```

q0, r0, q1, r1은 비공개 입력으로 제공되고, 회로는 관계식이 성립하는지만 검증합니다.

### 출력 노트 3개 (모두 스마트 노트)

| 노트 | 수신자 | 소유자 파생 |
|------|--------|-------------|
| 보상 (n0) | 테이커 | parentHash에서 |
| 지불 (n1) | 메이커 | makerHash에서 |
| 잔돈 (n2) | 상황에 따라 | 메이커 또는 테이커 해시에서 |

---

## 6. convert_note (스마트노트 변환)

스마트 노트를 일반 노트로 변환합니다.

### 공개 입력 (4개)

| 인덱스 | 이름 | 설명 |
|--------|------|------|
| 0 | output | 항상 1 |
| 1 | smartHash | 스마트 노트 해시 |
| 2 | originHash | 원본 노트 해시 (부모) |
| 3 | newHash | 변환 결과 노트 해시 |

### 회로가 검증하는 것

1. **스마트 노트 연결**:
   - `smartNote.owner0 == originHash >> 128`
   - `smartNote.owner1 == originHash & MASK`
2. **소유권**: 원본 노트(originNote)의 소유 증명
3. **가치/토큰 보존**: `smartNote.value/tokenType == newNote.value/tokenType`

## 회로 비용 분석

BabyJubJub 스칼라 곱셈(`EscalarMulFix`)이 비용의 97%+를 차지합니다.

```
소유권 증명 1회 ≈ 128K 제약 조건 (sk × G 계산)
Poseidon(7)    ≈ 1.7K 제약 조건
비트 연산      ≈ 0.3K 제약 조건
```

| 회로 | 소유권 증명 횟수 | 대략적 계산 |
|------|-----------------|-------------|
| mint_burn_note | 1 | 128K + 2K = ~130K |
| transfer_note | 2 | 256K + 260K = ~516K |
| make_order | 1 | 128K + 3K = ~131K |
| take_order | 1 | 128K + 130K = ~258K |
| settle_order | 1 | 128K + 513K = ~641K |
| convert_note | 1 | 128K + 257K = ~385K |
